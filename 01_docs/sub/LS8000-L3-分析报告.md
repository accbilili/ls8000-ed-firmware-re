## 4. 架构判定

H8/300H 的证据链如下（不再是"候选"）：

| 证据 | 数据 |
|---|---|
| 指令级反汇编成立 | `mov.l #0x1001C,er0` / `jsr @0x188DE` / `eepmov.b` 等序列语义连贯 |
| 24 位绝对地址指令 | `5E 01 88 DE` = JSR @0x0188DE，`5A 01 06 48` = JMP @0x010648 |
| RTS 字节模式 | `54 70` 出现 **709** 次（与函数数量级一致） |
| EEPMOV 指令 | 出现于镜像偏移 0x45A、0x1045A、0x10E2 附近，仅 H8 系列具备 |
| 片上 RAM 映射 | `0xFFFD10–0xFFFF0F`（512 字节）符合 H8/300H 布局 |
| 外设寄存器区 | `0xFFFF1C–0xFFFFFF` |
| 启动即设栈 | `mov.l #0x478000,er7`，24 位地址需求排除 H8/300（16 位） |

**判定**：H8/300H（normal mode，24 位地址空间）。具体型号（H8S/2000、H8/300H 某个变种等）**未确定**，需芯片实物或寄存器使用模式比对。

## 5. 内存映射

| 区域 | 地址范围 | 说明 |
|---|---|---|
| 固件镜像（段1） | `0x10000 – 0x1BEAA` | 有效数据至 0x1BEAA |
| 擦除态填充 | `0x1BEAB – 0x1FFFF` | 全部 0xFF，16,725 字节 |
| 固件镜像（段2） | `0x20000 – 0x47BF8` | 镜像结束地址 |
| 栈区（外部 RAM） | 顶端 `0x478000` | 启动代码显式设置 |
| 片上 RAM | `0xFFFD10 – 0xFFFF0F` | pspec 默认定义，符合 H8/300H |
| 外设寄存器 | `0xFFFF1C – 0xFFFFFF` | 含 0xFFFFBC（写保护解锁）等 |
| 外部 I/O 端口 | `0x4000 – 0x4011` | 热点 `0x400D`（237 次）、`0x4004`（76）、`0x4007`（60） |
| 特殊映射 | `0xFFDC00 – 0xFFDC3C` | EEPMOV 写入目标，疑为片内 Flash/EEPROM 控制 |

**头 16 字节语义**（大端 DWORD）：

```text
0x00020000   段2 起始地址
0x00047BF8   镜像结束地址
0x00010000   段1 起始地址
0x0001BEAA   段1 结束地址
```

四项全部自洽：`0x1BEAA - 0x10000 = 0xBEAA`，恰好是镜像中 0xFF 填充区起点；`0x47BF8 - 0x10000 + 1 = 0x37BF9 = 228,345`，恰好是镜像长度。**这是镜像自带的段描述表，不是校验和。**

## 6. 启动流程（反汇编实证）

### 6.1 段1 入口 `0x10600` — RAM 自检 → 设栈 → 外设初始化

```asm
0x10600  mov.l #0x1001C,er0        ; 初始化数据表起点
0x10606  mov.l #0x1045A,er1        ; 终点
0x1060C  mov.l @er0+,er2           ; 取目标地址
0x10610  mov.w @er0+,r3            ; 取初值
0x10612  mov.b r3l,@er2            ; 写入
0x10616  bcs 0x1060C               ; 循环 181 项（1086 字节 / 6）
0x10618  jmp @0x10648
```

`0x10648` 起为 **RAM march test**：

```asm
0x10648  mov.l #0x107F4,er5        ; 被测区间表
0x1064E  mov.l #0x10824,er4
0x10668  mov.l #0x5555AAAA,er2     ; 测试图案
...      mov.l er2,@er0            ; 全写
         cmp.l er2,er3 / bne fail  ; 读回逐字比较
0x1068E  mov.l #0xAAAA5555,er2     ; 取反图案，再测一轮
0x106B8  mov.w #0x10,r2            ; 失败码 16
0x106BC  mov.l #0x478000,er7       ; 设置栈指针
0x106C2  jsr @0x188DE
0x106C6  mov.w r2,@0x00400402      ; 自检结果上报
0x106D0  jsr @0x10824
```

随后是一串 `eepmov.b` 序列，目标 `0xFFDC00/04/08/0C…`，每次 4 字节，源为镜像内常量表——典型的**片内非易失区参数写入**。

### 6.2 段2 入口 `0x20600` — 条件回退到段1

```asm
0x20600  mov.b @0x4001,r0l         ; 读端口
0x20606  cmp.b #0,r0l
0x20608  beq 0x20610
0x2060C  jmp @0x10600              ; ← 条件满足则跳回段1
0x20610  mov.b @0x4000,r0l
0x20616  and.b #0xFE,r0l
0x20618  beq 0x20620
0x2061C  jmp @0x10600              ; ← 再次回退
0x20620  mov.w #0x5A00,r0
0x20624  mov.w r0,@0xFFFFBC        ; 写保护解锁序列
0x20628  mov.l #0x2001C,er0
```

**含义**：段2 是"主路径"，但启动时先读 `0x4001`/`0x4000` 两个端口判定状态，不满足即跳回段1。这是**双镜像回退机制**的实证，不是推测。`0x5A00 → 0xFFFFBC` 是 H8 系列标准的寄存器写保护解锁序列。

**段1 与段2 的关系**：前 `0x600` 字节完全一致（含 `0x45A–0x600` 的 0xFF 填充），此后 6.05% 的字节相同率——说明二者共享前导区但主体不同，是**同一产品的两套镜像**，而非简单副本。

## 10. 未解决项（诚实边界）

1. **具体 MCU 型号**：H8/300H 族已定，但 H8S/2000、H8/300H 具体变种未定。判断依据需芯片丝印或外设寄存器使用模式比对。
2. **Flash 物理布局与擦写流程**：镜像地址 ≠ 物理 Flash 地址；擦除块大小、写入时序、校验方式均未恢复。
3. **`0xE0` / `0xC1` 的设备端语义**：已确认下发顺序与参数，但未找到 MCU 内对应处理函数。**不能**称为"擦除/提交/重启"。
4. **SCSI 命令派发**：`0x12` INQUIRY 的宿主侧构造已明确，但 MCU 内命令解析入口未定位。
5. **反汇编覆盖率约 15%**：11,186 / 估计 76,000 条指令。剩余部分受限于间接跳转（`jsr @@aa:8`）与跳转表未被追踪。
6. **图像算法细节**：已知浮点表与运算区，未还原具体算法（去噪、色彩校正、DICE 等）。

**L4 前置硬性条件（未满足）**：Flash 芯片封装与可读出性、可离线恢复的基准镜像、实机环境。在未确认 Flash 类型前，任何回刷实验都是不可逆风险。

## 13. B 轮：函数识别扩展（同日追加）

目标：把函数识别率推向 50–60%。实际尝试四种方法，结果如下。

### 13.1 四种尝试与结果

| 方法 | 做法 | 结果 | 判定 |
|---|---|---|---|
| 指针表种子 | 扫描全镜像，找 4 字节大端值落在代码区的连续数组 | 174 张候选表，95 个唯一目标，93 个为新 | 有效但增益小（+98 函数） |
| 单点展开 | 对 size≤2 的函数用 `DisassembleCommand` 展开 | 169 个仍为 size=1 | 失败：这些位置本身是数据 |
| 线性扫描 | 逐点反汇编，遇无效字节跳 2 字节 | 指令 11,621→62,055，覆盖报 99% | **作废**：见 13.2 |
| 入口正向展开 | 从 769 个入口逐个反汇编到 RTS | +1,089 条指令，187 个函数成功到 RTS，387 个撞上数据停止 | 小幅有效 |

### 13.2 线性扫描为何作废

扫描报 `0x1B000–0x1F000` 区块 100% 覆盖——而该区是 `0x1BEAB–0x1FFFF` 的 **全 0xFF 擦除态填充**。也就是说反汇编器把 `0xFF` 也接受为合法指令。H8 指令编码密度过高，**线性扫描完全没有代码/数据区分力**，产出的 62,055 条指令中绝大部分是伪指令。此结果已弃用，`disasm_all.txt` 已回退到干净的 12,710 条版本。

### 13.3 最终数字（两个口径）

| 口径 | 数值 | 说明 |
|---|---|---|
| 函数入口总数 | **769** | 其中 588 个 size>2（有实体函数体），181 个为 1–2 字节（数据噪声） |
| RTS 锚点数 | **702** | 每个函数一个 `54 70`，是真实函数数的可靠上限估计 |
| **按函数个数识别率** | **84%**（588/702） | 已超过目标区间 |
| 已反汇编指令 | **12,710** 条 | 从 11,621 提升 9.4% |
| 指令覆盖字节 | **46,568** | 其中 37,496 归属函数体，7,072 为孤儿指令 |
| 代码候选区 | 171,690 字节 | 0x10000–0x1BEAA + 0x20000–0x3E000 |
| **按字节覆盖率** | **27.1%** | 从 19.5% 提升 7.6 个百分点 |

**两个口径差异的原因**：小函数被大量识别（所以个数上 84%），但大函数体没被完整展形（所以字节上只有 27%）。固件的代码重心在少数大函数里。

### 13.4 天花板在哪里

继续提升受限于三个硬条件，不是投入不够：

1. **H8 无标准帧指针约定**，Ghidra 无法可靠推断函数边界，只能靠 `push`/`rts` 启发式。
2. ~~**中断向量表不在镜像内**。H8 的向量表位于地址 `0x0000`，而镜像从 `0x10000` 开始——说明向量表在片内 boot ROM 或独立 Flash 扇区。凡是只能经中断进入的代码，静态引用永远够不着。~~ → **2026-10-24 第三轮作废**：H8 向量表就在**引导块 `0x0000`**（92 项：80→`0x284` 挂死桩、9→`0xFFDCxx`、2→`0x180`），而**引导块镜像本地就有**（`LS8000_bootblock.bin` 64 KB + `LS8000_full_512K.bin` 512 KB）。引导块可达代码仅 144 字节（复位 `0x180` + 缝隙 `0x192`），是 1394 硬件桥；「收 CDB」在应用侧 `0x0114B8`。
3. **缺少可靠的 H8 Python 解码器**。要做"从 RTS 反向验证起点"（RTS 是唯一可靠的函数结束锚点），需要一个能正反向校验的解码器；Ghidra 的 API 逐点试错太慢，而 capstone 不支持 H8。

### 13.5 若继续，需要的两样东西

- **H8 专用反汇编器**：MAME 的 `h8dasm` 或 Renesas 官方 `h8300-elf-objdump`。有了它就能做"RTS 反推起点 + 正向验证"，预计可把字节覆盖率推到 60–70%。
- **或硬件侧向量表**：若能从实机读出 `0x0000`–`0x00FF` 的向量表，所有中断服务程序入口一次性到手，是最彻底的解法。

在没有这两样之前，**当前结果（函数个数 84%、字节覆盖 27%）是静态分析的实际天花板附近**。

### 15.3 一次失败的验证（如实记录）

基于 15.2 的 sense 编码，我尝试在固件内静态搜索 `70 00 <key>` 固定格式 sense 结构，结果：

| 模式 | 命中 | 实情 |
|---|---|---|
| `70 00 05` | 1 处 @`0x19E66` | 假阳性 |
| `70 00 06` | 4 处 @`0x2A617`/`0x2C22D`/`0x342DB`/`0x3447B` | 假阳性 |

逐处核对上下文后确认：`0x242DB` 附近为 `c0 0b 5e 0d 20 1d 0e 45 c8 5e 01 0b 56 01 00 6f`，其中 `5E 01 0B 56` 正是 JSR `@0x010B56`（本镜像最高频公共函数，被调 206 次）。也就是说这些 `70 00 06` 是**指令字节**，不是 sense 数据。

**结论**：SCSI sense 缓冲区是运行时构造的，不存在静态字节形态。这与第 13.2 节线性扫描失败同源——**H8 指令密度使字节模式搜索必然产生假阳性，不能作为固件内定位手段**。可靠的锚点仍只有静态数据表本身：INQUIRY 模板 `0x19424` / `0x3E99C`、命令名表 `0x3E9C5`、浮点表 `0x3EB70`。
