# `host_code` 到底从哪来（G2 定案）

日期：2026-10-24 · 输入 `LS8000_111_ROM.bin`（地址 = 文件偏移 + `0x10000`）、`cfg_v4.json`、
`xrefs_data.csv`、`LS8000.md3`
方法：反汇编判据 + 全镜像写点普查 + 主机侧 PE 立即数扫描
边界：纯静态，未执行任何命令

---

## 0. 一句话结论

**`host_code` 是固件自己写死的 16 位内部状态码，不是主机下发的。**
它落在 RAM 的 `0x400402`（低字）/`0x400404`（高字）两个单元上，由两台内部状态机用**立即数常数**
（`mov.w #0x0810` / `or.w #0x0830, r0` 形态）写入；主循环每轮轮询这两个单元，拿去查 `0x03E390`。

对接面判定：**(b) 变体 —— 固件自己产生，但既不由 SCSI opcode 算出，也不由 E0 子功能码派生，
而是由「内部状态机当前所处的步骤」决定。**（详见 §3）

## 1. `0x01750E` 的入参来源（逐条到最初来源）`[实证]`

### 1.1 函数头：入参是一个 32 位字，被拆成两个 16 位

`0x01750E` 属于函数 `0x0174BC`（`cfg_v4.json` owner 判定）。函数头两条指令把 `er0` 拆开：

```asm
0x0174BC  mov.l     er6, @-sp
0x0174C0  mov.l     sp, er6
0x0174C2  mov.l     er5, @-sp
0x0174C6  subs.l    #4, sp
0x0174C8  subs.l    #4, sp
0x0174CA  mov.w     r0, r5        ; r5 = er0 低 16 位  ← 第 1 个 host_code
0x0174CC  mov.w     e0, e5        ; e5 = er0 高 16 位  ← 第 2 个 host_code
0x0174CE  mov.b     @0x449b0e, r0l
...
0x0174EA  mov.w     @0x449b0a, r0   ; 缓存的上次高字
0x0174F0  cmp.w     e5, r0          ; 与本次高字比 → 未变则跳过
0x0174F2  bne       0x017500
0x0174F4  mov.w     @0x449b08, r0   ; 缓存的上次低字
0x0174FA  cmp.w     r5, r0
0x0174FC  beq       0x0175a4
0x017500  mov.w     e5, e5
0x017502  beq       0x01759c        ; 高字 == 0 → 不查
0x017506  mov.w     r5, r5
0x017508  beq       0x01759c        ; 低字 == 0 → 不查
0x01750C  mov.w     e5, r0          ; ★ 查表入参 = e5（高字）
0x01750E  jsr       0x0211b6        ; ★ 查 0x03E390
0x017512  mov.w     r0, @(0xfff4,er6)
...
0x0175B6  mov.w     r5, r0          ; ★ 第二次查表入参 = r5（低字）
0x0175B8  jsr       0x0211b6
```

`0x449b08` / `0x449b0a` 是「上次已上报的 (低, 高)」缓存，用来做**边沿触发**——只有状态变了才重新查表上报。
这本身就说明 `host_code` 是**状态**，不是**命令参数**（命令参数不需要去抖）。

### 1.2 调用点：两个主循环把 RAM 里的两个字装进 `er0`

`0x0174BC` 全镜像只有两个调用者，形态完全一致：

```asm
; —— 段 2 主循环 0x020B84 ——
0x020BC2  mov.w     @0x400404, e0     ; e0 = *(u16*)0x400404  → 高字
0x020BC8  mov.w     @0x400402, r0     ; r0 = *(u16*)0x400402  → 低字
0x020BCE  jsr       0x0174bc
0x020BD2  mov.l     @er4, er0
0x020BD6  beq       0x020bde
0x020BD8  mov.l     @er4, er0
0x020BDC  jsr       er0               ; ← 间接调用“当前任务”函数指针

; —— 段 1 主循环 0x011078 ——
0x0110B0  mov.w     @0x400404, e0
0x0110B6  mov.w     @0x400402, r0
0x0110BC  jsr       0x0174bc
```

**结论链（每跳都有地址）：**

```
*(u16*)0x400404 ──┐
                  ├─ er0(高:低) ── 0x0174CA/CC ── e5 / r5 ── 0x01750C ── r0 ── 0x0211B6
*(u16*)0x400402 ──┘
```

`0x400402`/`0x400404` **不是** CDB 缓冲（CDB 在 `0x40043C` 起，见 `0x021776 mov.l #0x0040043c, er4`，
那是 SCSI `0x03` REQUEST SENSE 的处理器）。二者相距 0x3A 字节，无任何代码把 CDB 字节搬到这两格。

`host_code = 族常数 | (内部小索引 + 1)`，索引来自固件自己的 RAM 状态字节。
**没有任何一条是「从 CDB 取字节拼出」。**

### 1.5 反证：CDB 确实用，但不进这两格 `[实证]`

`0x021768`（SCSI `0x03` REQUEST SENSE）`0x021776 mov.l #0x0040043c, er4` 直接读 CDB；
`0x02159C`（SCSI `0x00` TUR）`0x0215B6 mov.b @0x40043d, r0l` / `0x0215CA mov.b @(0x40043c,er0), r1l`
遍历 CDB[0..5] 做「是否全零」检查。但这些 CDB 字节**只用于合法性判断**，
随后 `0x0215F2 mov.w @er5, r0`（`er5`=0x400402）取的状态码仍然是内部状态。

## 2. 调用链上溯 `[实证]`

### 2.1 消费侧（读 host_code 去查表）

```
段2 主循环 0x020B84 ──jsr 0x020BCE──> 0x0174BC ──jsr 0x01750E/0x0175B8──> 0x0211B6
  ↑ jmp 0x020C26（自循环，0x020C26 在 0x020BE2 块内）        （查 0x03E390）
段1 主循环 0x011078 ──jsr 0x0110BC──> 0x0174BC
  ↑ jmp 0x01115C（0x011000 块内）
```

**两条链都终止于主循环，不终止于任何命令入口。** 这本身就是关键结论：
`host_code` 的查表上报是**后台轮询**，不是命令执行路径的一部分。

### 2.2 产生侧（写 host_code）

写入者都不在 SCSI 分派链上。以三条最典型的为例：

```
0x027930（写 #0x3000/#0x9000）
  ↑ bsr 0x0276FA   (in 0x027676)
      ↑ bsr 0x02755E (in 0x02753E)      ← 0x02753E 是 0x0274BC 的 fall-through 块
          ↑ 0x0274BC 状态机（无静态调用者）

0x03B0E8（写 #0x0920/#0x0930）  —— 无静态调用者
0x02842C（写 #0x0F20/#0x2000）  —— 无静态调用者
```

`0x0274BC` / `0x02842C` / `0x03B0E8` / `0x0311E4` / `0x03D40E` 在 `xrefs_data.csv` 与
`cfg_v4.json` 中**均无 `jsr`/`bsr` 调用者**，也**不是**任何 ROM 数据表里的函数指针
（已用 32 位大端指针全镜像搜索验证：0 命中）。它们的唯一入口是主循环
`0x020B84` 中 `0x020BD2-0x020BDC` 的**间接调用**：

```asm
0x020BD2  mov.l     @er4, er0     ; er4 = RAM 中的“当前任务”槽位
0x020BD6  beq       0x020bde
0x020BD8  mov.l     @er4, er0
0x020BDC  jsr       er0           ; ← 状态机由此进入
```

即：固件维护一个「当前任务」函数指针槽，主循环每轮调一次；哪个状态机在跑，
就由它写入当时的 `host_code`。**命令只是「启动某个任务」，不传状态码。**

### 2.3 完整骨架（每跳标注）

```
[主机] ──CDB──> 0x020E86 SCSI 分派（表 0x03E2E8，20×8B，code/opcode→handler）
                    │
                    ├─ 设置内部任务槽（RAM 函数指针）
                    └─ 返回
                           ⋮（异步）
主循环 0x020B84 ──jsr er0 @0x020BDC──> 内部状态机 0x0274BC/0x02842C/0x03B0E8/…
                                            │ mov.w #imm, @0x400402 / @0x400404
                                            ▼
主循环 0x020B84 ──jsr @0x020BCE──> 0x0174BC ──jsr──> 0x0211B6 ──> 0x03E390
                                            │
                                            ├─ *5 + 0x01914A（0x01751E/0x017520）
                                            └─ 写 0x449AF1..0x449AF4（0x017556..0x017586）
                                                     ↓
                                        由 0x016F46 组装 0xAA 状态块偏移 0x12..0x15 上报主机
```

也就是说命令入口（`0x020E86`）与 `host_code` 之间**隔着一层异步任务调度**，
没有直接的数据流边——这正是「不是主机下发」的结构性证据。

## 3. 对接面定论

| 选项 | 判定 | 依据 |
|---|---|---|
| **(a) 主机经 CDB 明文下发** | **否** | 20 处写点全为立即数（§1.4）；CDB 字节与 `0x400402`/`0x400404` 无数据流（§1.5）；md3 反例检查阴性（§5） |
| **(b) 固件据 opcode+参数算出** | **部分** | 确实是固件自己产生，但**不由 opcode 推导**：写入者全部是内部状态机，不在 SCSI 分派链上（§2.2）；同一 opcode（如 `0x24` SET WINDOW）可导致完全不同的 `host_code`，取决于执行到哪一步 |
| **(c) 由 E0 子功能码派生** | **否** | E0 子功能码落 `0x400C55`，`0x03EDB8` 表只有 8 个 8 位码（`80/81/A0/B0/C1/D0/40/41`），与 85 个 16 位 `host_code` 无交集；E0 handler `0x026BF8` 不在写入者链上 |

**定论（写 17.1 用）**：`0x03E390` 是**固件内部状态/条件码 → 上报描述符**的翻译表，
不是主机命令映射表。把它当"主机码表"是命名误导：建议改称
**`status_code`（内部状态码）表**，`host_code` 这个字段名应当废止或加引号。
主机能影响它的唯一途径是「发命令启动某个内部任务」，任务跑到的步骤决定码值。

## 4. 85 条语义推断（按高字节分组）

`[实证]` 基础：每条 `host_code` → `field2` → `0x01914A + field2*5` 的 5 字节记录，
其中 `[b1b2]` 是一个 `u16` "kind"，共 12 种。下表 `kind` 取自实测记录。

| 高字节 | 条数 | kind 分布 | 代表码 | 由谁写（地址） | 语义判断 |
|---|---|---|---|---|---|
| `0x08` | **44** | `0460`×32 `0411`×7 `0311`×5 | `0800`–`08B4` | `0x030780`–`0x03554A`、`0x03D428`（`0x0810/0830/0860/0890` 四个族常数） | **[推断]** 扫描/图像采集族。低字节高半字节=参数组（11 组：`08 0/1/3/4/5/6/7/8/9/A/B`×0x10），低半字节=轴/通道 1–4。写入块含 `0x41FF74/0x41FF76`（疑似 ASIC 图像寄存器）与 `cmp.w #0x0040, e4` 的 64 次循环 |
| `0x06` | 10 | `0311`×5 `0460`×5 | `0600`–`0614` | 同 `0x08` 族区（`0x030xxx`–`0x035xxx`） | **[推断]** 扫描族的第二参数区，与 `0x08` 共享 kind，是另一组通道 |
| `0x09` | 9 | `0311`×5 `0161`×4 | `0910`–`0950` | `0x03B4D2/#0x0920`、`0x03B4D8/#0x0930` | **[推断]** 位置/校准族。`091x` 与 `0x08` 族同 kind `0311`；`0920/0930/0940/0950` 独占 kind `0161`，写入处 `0x03B410 cmp.w #0x01c2, r6`（450）与 `0x03B3EE cmp.l #0x000000a0`（160）是限位比较 |
| `0x0F` | 6 | `0444`×3 `0403` `0408` `0415` 各 1 | `0F10`–`0F60` | `0x0285DE/#0x0F20` | **[推断]** 状态/模式族。`0x0F20` 与 `#0x2000` 成对写入（`0x0285E2`+`0x0285EC`），条件为 `(*0x400406 & 0xFF) == 0x80`；同块 `0x02859E` 写 `0x4003FB = 0x10`（片夹类型码），故与片夹/进片状态强相关 |
| `0x01` | 4 | `0415`×3 `0462`×1 | `0110` `0120` `0121` `0122` | `0x02AFE8`/`0x02B02C`/`0x02CBCA`（均为 `#0x0110`） | **[推断]** 机械/马达族。`0x0110` 三处写入都在等 `0x44080E` 命令应答（`0x02AFB2 jsr 0x02cf40` + `0x02AFD8 jsr 0x010b56` 就绪等待），应答不等于 2 时置 `0x0110` |
| `0x05` | 3 | `0453`×3 | `0500` `0501` `0502` | 未定位到写点 | **[未证]** kind 单一，疑为同一子系统的三档 |
| `0x10` `0x11` `0x20` `0x30` `0x50` `0x0E` | 各 1 | `0204`×6 | `1000` `1100` `2000` `3000` `5000` `0E10` | `0x0279B2/#0x3000`、`0x0285EC/#0x2000` | **[推断]** 顶层运行模式族，kind 全为 `0204`。`0x3000` 由进片状态机 `0x027930`（该块读 `0x4003FB`）在 `0x02799C jsr 0x0289b4` 成功后写；`0x2000` 由 `0x02842C` 写。这两个码还在 `0x017600/0x017606` 被显式比较，说明有特殊语义 |
| `0x40` `0x90` | 各 1 | `023A`×2 | `4000` `9000` | `0x027A14/#0x9000` | **[推断]** 与 `0x3000` 同属进片状态机 `0x027930`：`0x3000`=识别成功路径（`0x02799A bne` 分支），`0x9000`=兜底/失败路径（`0x027A10` 无条件写）。`0x4000` 未定位写点 |
| `0x04` | 1 | `0415` | `0430` | 未定位 | **[未证]** 与 `0x01` 族同 kind，疑机械类 |

**带依据的断言（可写进 17.1）：**

1. `[实证]` 同族 `kind` 高度一致（`0x06` 全族 `0311/0460`，`0x05` 全族 `0453`，
   `0x10/0x11/0x20/0x30/0x50/0x0E` 全族 `0204`），证明高字节是**子系统编号**而非随机编号。
2. `[实证]` `0x08` 族是可枚举的二维矩阵：11 个组 × 索引 0–4，与 `or.w #0x08x0` 的四个实测族常数
   （`0810/0830/0860/0890`）吻合——低字节高半字节选族常数、低半字节是通道号。
3. `[推断]` `0x4003FB`（片夹类型码）与 `0x0F20/0x2000/0x3000/0x9000` 由**同一批**函数写入
   （`0x02842C` 写 `0x4003FB` 又写 `0x0F20`；`0x027930` 读 `0x4003FB` 又写 `0x3000/0x9000`），
   故这几个族归属**片夹/进片子系统**。
4. `[推断]` `0x0110` 与马达命令应答寄存器 `0x44080E` 强绑定 → **机械执行族**。
5. `[实证]` 与已知 SCSI 命令**完全无法对应**：85 个码的高字节集合
   `{01,04,05,06,08,09,0E,0F,10,11,20,30,40,50,90}` 与 SCSI 分派表 `0x03E2E8` 的 opcode 集合
   `{00,03,12,15,16,17,1A,1B,1C,1D,24,25,28,2A,3B,3C,C0,C1,E0,E1}` **交集为空**。
   与 E0 子功能表 `0x03EDB8` 的 8 位子功能码 `{80,81,A0,B0,C1,D0,40,41}` 交集为 `{0x40}`，
   但二者位数不同（`host_code` 的 `0x40` 是 `0x4000` 的高字节，子功能码 `0x40` 是 CDB[2] 的 8 位值），
   且 `0x4000` 的写点不在 E0 handler `0x026BF8` 链上，判为**巧合**。

## 5. 反例检查（md3 硬证据）

### 5.1 方法可靠性说明（回应任务书的要求）

任务书说「字节搜索在 H8 代码区假阳性极高，但在 x86 的 md3 里搜立即数可靠」——
**这个说法只对一半，必须修正：**

- **H8 侧确实不可靠**：H8/300H 指令定长 2/4/6/8 字节，任何 2 字节都能解码成合法指令，
  字节序列无自同步性。所以本文所有固件侧结论**一律不靠字节搜索**，只用
  `cfg_v4.json` 的解码操作数做引用扫描（`_g2/util.py`）。
- **x86 侧也并非天然可靠**，原因不同：x86 是变长指令、无自同步，**线性/滑动窗口反汇编
  会把内联数据解成假指令**。本轮实测：对 `.text` 做「滑动窗口回溯 ≤8 字节」搜索时，
  出现 `enter 0x874, -0x75`、`ljmp 0xf20:0x51af0f03`、`lcall 0x851, 0xe8000000`
  这类明显误解码（全 `.text` 命中 43/85，其中大量是这种噪声）。
- **可靠的前提是先有 CFG**。因此定稿数字只用 `md3/cfg_funcs.txt`（1241 个已确认函数体、
  含精确指令数）做种子，再叠加 `calls.pkl` 的全部 call 目标，按「遇 `ret` 停」反汇编。

三档结果并列报告：

| 口径 | 覆盖 | 命中 | 可判别（低字节≠0） | 说明 |
|---|---|---|---|---|
| 严格（CFG 函数体，精确指令数） | 13,616 条指令 ≈ **5.6%** `.text` | **6 / 85** | **1**（`0x0110`） | 该 1 处是 `0x10025002 add edi, 0x110` —— 结构体偏移，噪声 |
| 宽（CFG 入口 + 全部 call 目标） | 260,517 条指令 ≈ **34.1%** `.text` | **20 / 85** | **13** | 定稿采用 |
| 滑动窗口（无 CFG） | 100% 字节 | 43 / 85 | ~28 | **弃用**，误解码过多 |

### 5.2 定稿统计（宽口径，34.1% 覆盖）

**85 个 `host_code` 里，作为 x86 立即数在 md3 `.text` 中出现的：20 个；其中可判别（非整千/整百通用常量）的 13 个。**

可判别 13 个及其所在函数（`md3/funcs.txt` 命名，未命名者记 `sub_xxxxxxxx`）：

| `0x0830` | 2 | `0x100B00B5 / 0x100B012F test word ptr [ebp-8], 0x830` |
| `0x0810` | 2 | `0x100B00D2 / 0x100B013F test word ptr [ebp-8], 0x810` |
| `0x0851` | 1 | `0x100520F5 push 0x851` |
| `0x0860` | 1 | `0x10015C47 push 0x860` |

### 5.3 更硬的阴性证据：与 MAID 能力表比对

`md3/dispatch_caps.json` 有 **268 条** `cap_id`（`group` = 高字节，`sub` = 低字节）。
85 个 `host_code` 与之**精确相同的只有 2 个**：

- `0x4000` → cap `0x40/0x00`，handler `0x1004BC10`
- `0x1100` → cap `0x11/0x00`，handler `0x10064380`

而且 md3 能力 group 分布是 `0x50`×117、`0x54`×69、`0x60`×29、`0x52`×21、`0x40`×10、`0x80`×8、`0x81`×6……，
与固件 `host_code` 的高字节分布（`0x08`×44 为首）**几乎不相交**。
这两个命中更像巧合（16384 / 4352 都是常见整数），不构成命名空间对齐。

**结论**：md3 **不能**构造出这 85 个码，`0x03E390` 与 md3 的 MAID 能力/选择子**不是同一套编号**。
第 17.1 节「把主机侧能力枚举与 48/85 条 host_code 对齐」这条路线应当**作废**。

### 5.4 与 `md3/cdb_sites.md` 的一致性

`cdb_sites.md` 已实证 md3 造 18 条 CDB，CDB 字段来源全部可追溯
（子功能码经 `0x100AA1D0` 白名单化后落到 **CDB[2]，是 8 位**）。
16 位的 `host_code` 在 CDB 里**没有承载位置**——与本轮固件侧结论互为印证。
`0xD1` 会被发出这条也仍是 8 位子功能码，与本议题无关。

## 7. 本轮未解决的疑问

1. **`0x400402` / `0x400404` 的准确命名**未定。已证是「当前状态码（低/高）」，
   但高字只在 `0x3000`/`0x9000`/`0x2000` 三处被写，低字有 17 处，二者是否构成
   「主状态 + 子状态」还是「前次 + 当前」需要看 `0x02159C` 的完整分支（`0x0216C4` 处比较 `*0x400404 == 0x9000`）。
   下一步：把 `0x02159C` 全文反汇编完，给出两格的读法。
2. **`0x0920`/`0x0930` 的写点 `0x03B0E8` 无静态调用者**，与 `0x0274BC` 等一样靠
   `0x020BDC jsr er0` 进入。这个「当前任务槽」（`er4` 指向的 RAM 单元）地址未定位——
   它是怎么被设置的、由哪个命令处理器设置，决定了「命令 → 状态码」的完整映射。
   下一步：追 `0x020B84` 入口处 `er4` 的初始化来源（往 `0x020600` 段入口方向找）。
3. **65 个 host_code 在 md3 中完全未出现**，且 md3 CFG 只覆盖 `.text` 的 34.1%。
   阴性结论的强度受覆盖率限制。若要坐实，需要把 md3 的 CFG 覆盖率提到 80% 以上
   （可用 `md3/scan_jmp.py` 的跳转表扫描补齐 switch 分支）。
4. **`0x0121`（9 次）与 `0x0122`（9 次）在 md3 中成对出现**于 `push` 立即数
   （`0x1007DEDB`/`0x1007DF5C`、`0x1008885B`/`0x100888DC` 等），与固件 `0x0121→0x2A`、
   `0x0122→0x77`（同为 kind `0415`）成对出现形态相似。**这可能是唯一一条真线索**，
   但未证。下一步：反汇编 `0x1007DE00`–`0x1007E000` 与 `0x10088800`–`0x10088900`，
   看 `0x121`/`0x122` 被传给谁。
5. **`0x400436` 的双重身份**（`table_03E390.md` 疑问 2）本轮仍未解决。
   本轮新增线索：查表结果会被写进 `0x400438`（`0x02172C mov.w r0, @0x400438`），
   与 `0x400436` 相邻，提示 `0x400436`/`0x400438` 是一对 16 位上报字，
   但仍缺写入者时序证据。
