## 1.2 曾经的唯一结构性缺口 —— **2026-10-24 第三轮作废**

> **原结论（已作废）**：「引导块 `0x000000–0x00FFFF`（64 KB）不在镜像内，是唯一结构性缺口，唯一途径是器件 flash dump 或 SCSI READ BUFFER 试读」。
> **作废理由**：该判断源于「应用镜像（`0x10000` 起）不含向量表」这一**局部**观察，忽略了**引导块镜像与全图本来就在本地样本里**：

| 文件 | 大小 | 校验 |
|---|---|---|
| `D:/DS/TEST/LS8000/LS8000_bootblock.bin` | 65,536 B | 引导块 `0x0–0xFFFF`，**地址 = 文件偏移** |
| `D:/DS/TEST/LS8000/LS8000_full_512K.bin` | 524,288 B | `full[0:0x10000]==bootblock`、`full[0x10000:0x10000+228345]==111_ROM` ✓ |

早前未发现，成因是列目录被 `ls | head -30` 截断（见 §10.14 M9）。**引导块侧分析已全部完成（代码侧 + 数据侧），详见 §14.1 与 §14.2.2。**

补充（仍然成立）：头部字面量证明应用从 `0x10000` 开始；622 个已恢复函数中**无 `ldc VBR` / `stc VBR`** → 固件不重定位向量表，H8 向量表固定在地址 0（即引导块 `0x0000`）。
- 在所有 2 字节对齐偏移检索 256×u32 向量表（要求 ≥40 个不同项且 ≥150 项可解码），**0 命中**

补它只有两条路：① 器件 flash dump（需拆机/夹子读出）；② 若 `READ BUFFER` 允许读 `0x0–0x7FFFF`，可试 SCSI 只读读取——但这属主动访问设备，未执行。

## 1.3 为什么不必补引导块

按用户目的（"只是想看看固件"），L3 的定义是"理解固件架构"，不要求"理解整台设备"。引导块缺失影响的是：
- 中断进入的代码路径（ISR）
- 复位向量
- 1394/SCSI 收包并填入 CDB 的代码

不影响：应用层命令分派、数据表、片夹识别、机构参数、图像参数。这些**全部在应用区内**。

## 3.2 头部 28 字节（全自洽，`[实证]`）

| 偏移 | 值 | 含义 | 校验 |
|---|---|---|---|
| `+0x00` | `0x00020000` | 第二副本起点 | = base + 0x10000 ✓ |
| `+0x04` | `0x00047BF8` | 镜像末地址 | = base + len - 1 ✓ |
| `+0x08` | `0x00010000` | 自身起点 = ROM 基址 | = base ✓ |
| `+0x0C` | `0x0001BEAA` | 第一副本结束（擦除区起点） | = base + 0xBEAA ✓ |
| `+0x10` | `0x0DBACFC9` | 未解（疑似构建 ID） | — |
| `+0x14` | `0xCBD0CFE0` | 未解（疑似构建 ID） | — |
| `+0x18` | `0x00009448` | 构建信息块地址 | 见 §3.4 |

四项互相咬合，**不是校验和**。这是确定 ROM 基址 `0x10000` 的决定性证据。

## 3.3 初始化表（`0x1001C` 起）

181 条 6 字节记录：`[u32 目标地址][u16 值]`。

| 目标域 | 条数 | 含义 |
|---|---|---|
| `0x00FFFFxx` | 55 | H8/300H 片上 I/O 寄存器 |
| `0x0020xxxx` | 126 | ASIC / FPGA 寄存器 |

样例：

## 3.4 构建信息块 `0x19448`

头部 `+0x18` 指向 `0x19448`。同时该地址也是**升级时 24 字节版本标记比对的 ROM 侧目标**（主机送 `0x400D3D`，与 `0x019448` 比对）。这一地址被两处独立引用，属高置信锚点。

## 3.5 擦除区

`0x1BEAA–0x1FFFF` 共 **16,726 字节全 `0xFF`** `[实证]`。

意义：闪存页擦除态。说明第一副本实际使用到 `0xBEAA` 为止，其后是未编程空间。

# 第 4 章 架构判定

## 4.1 结论

**H8/300H**（日立/Renesas），24 位地址空间、**大端**、16 位定长指令基。

## 4.2 三条独立路径同结论

这三条路径来自三套不同工具、不同方法，互不引用：

| 路径 | 方法 | 工具 |
|---|---|---|
| A | 自建 H8/300H 反汇编器 + MAME 393 条编码表 | DeepSeek Harness 的 `h8dis.py` |
| B | 按 H8/300H 手册逐字节比对指令格式 | Codex（`~/.codex` 会话） |
| C | 编译 sleigh 语言定义装入 Ghidra，语言 ID `H8:BE:32:H8300` | WorkBuddy 本轮 |

> 路径 C 的实现细节：Ghidra 12.1.4 官方**不含 H8 处理器模块**。取 `carllom/sleigh-h8`（其 `h8300h.slaspec` 用 32 位地址空间，正好容纳 `0x10000` 以上的镜像，无需改），用 Ghidra 自带 `support/sleigh` 编译出 `h8300h.sla`，装到 `Ghidra/Processors/h8/data/languages/`。另一个候选 `Thodoris1999/H8-38602R` 地址空间是 16 位（标 `H8:BE:16:H8300`），装不下本镜像，除非改 slaspec 并解决指针宽度冲突，不推荐。

# 第 6 章 启动流程

## 6.1 段1 入口 `0x10600`

```asm

         写 0xAAAA5555 → 读回

         mov.l #0x478000, er7          ; ★ 设置栈指针到 0x478000

         eepmov.b                      ; 写 0xFFDC00
```

## 6.2 段2 入口 `0x20600` — 双镜像回退（`[实证]`）

```asm
0x20600  mov.b @0x4001, r0l           ; 读端口 0x4001
0x206xx  mov.b @0x4000, r0l           ; 读端口 0x4000
0x206xx  cmp / bne
0x206xx  jmp @0x10600                 ; ★ 条件不满足 → 跳回段1 执行
0x206xx  mov.w #0x5A00, r0
0x206xx  mov.w r0, @0xFFFFBC          ; ★ 写保护解锁序列（同时触发 ASIC）
```

**这不是推测**：`jmp @0x10600` 是显式的，段1 的完整代码在同一镜像内可用。构成"段2 检测失败 → 回退段1"的降级路径。

## 6.3 主循环 `0x020B84`

```
0x020B84  jmp 0x020B84                ; 无限循环，每轮：
   ├─ 轮询 0x01476A / 0x010B56 / 0x027A54
   ├─ 排队回调（jsr er0）
   ├─ 命令分派器 0x020E86 → 表 0x03E2E8
   └─ jsr 0x000192                    ; ★ 引导块唯一入口，每轮一次
```

`0x010B56` 是**全固件最通用的同步原语**（设备就绪等待），被调用 206 次。

## 6.4 引导块接口

应用对引导块的调用**仅一处**：`jsr 0x000192`。

> 已逐点否证的假阳性：`0x6B80` / `0x6BA0` / `0x69B0` / `0x0117` / `0x0201` / `0x0219` / `0x0246` 等低地址"调用"，全部是解码错位。例：`0x0109F8` 处字节 `5A 00 6B 80` 恰好跨在 `7900 5a00` 与 `6b80 ffbc` 两条指令之间。

## 7.4 E0 解析层与 C1 执行层的两段式结构（`[实证]`，2026-10-24 第三轮更正）

> **第三轮更正**：早前把 `0x0269A6` 称作「E0 执行层」是错的。分派表 `0x03E2E8`（20 条 × 8 B，`0x03E388` 全零终止）实测：
>
> ```
> [16] op=0xC0 f3=000754 fn=0x02694A
> [17] op=0xC1 f3=000014 fn=0x0269A6   ← C1（EXECUTE）处理函数
> [18] op=0xE0 f3=000014 fn=0x026BF8   ← E0 处理函数（解析 + 数值门限 + 落存）
> [19] op=0xE1 f3=000014 fn=0x026EFC
> ```
>
> **协议是两段式**：E0 只做解析/门限/落存（`0x400C55` = 子功能码、`0x400C56+i` = payload、错误码 `0x50`/`0x53` → `0x400436`），**C1（EXECUTE）才触发 12 值开关**（8 臂 + default `0x56`）。与主机侧 §13.2.1「C1 = EXECUTE、C1 的 CDB 不带子码」自洽。

### 7.4.1 开关全貌（`0x0269A6`）

入参 `er6 = 0x400C55`（子功能码区）、`er4 = 0x400436`（状态输出）、`er5 = 0x400410`。
**入口前置校验（第三轮新增）**：`0x0269C0–0x0269E4` 要求 `mem[0x40043D]&0x1F==0` 且 `mem[0x40043E..0x400441]==0`，否则 `0x400436 ← 0x50`。

| 子功能 | 落点 | 表声明长度 | 代码实读偏移（`er6` 相对） | 行为 |
|---|---|---|---|---|
| `0x40`/`0x41`/`0x42` | `0x026A3E` | 11 | `0x0A`,`0x0B` | 拼 16 位后 **`0x026A50 sub.w r0,r0` 清零** → `0x400410 ← 0x0000`，且**落穿进 C1 臂体**（`0x026A54` 起）→ 一并写 `0x400408` |
| `0x80` | `0x026A2E` | 0 | 无 | 置 `0x400D3B` = 1，跳 `0x026BEE` 收尾（**不走公共尾**） |
| `0x81`/`0xB0`/`0xD0` | `0x026BD2` | 0 | 无 | 无数据动作，共出口 |
| `0x91`/`0x92` | `0x026BB2`/`0x026BBE` | 5 | `0x02`–`0x0D` | 写 `0x400413`/`0x400414`、`0x42029E`/`0x42029F`（**第三轮展开**） |
| `0xA0` | `0x026A92` | 9 | `0x02`–`0x09` | `0x400408 ← payload[1..4]`；`0x40040C ← payload[5..8]`（**不读 payload[0]**） |
| `0xB3` | `0x026B0A` | 13 | `0x01`–`0x0D` | 13 字节全部映射：`p0→0x400412`、`p1..p4→0x400408`、`p5..p8→0x40040C`、`p9,p10→0x400410/0x400411`（16 位 BE）、`p11→0x400413`、`p12→0x400414`（**第三轮展开**） |

0x026BD4  extu.w r0

### 7.4.2 `0x400408` 的 32 位大端组装（`0x026A54`，实测）

```asm
0x026A54  sub.l  er0, er0
0x026A56  mov.b  @(0x2,er6), r0l   ; b2 = payload[1]
0x026A5A  mov.b  r0l, r0h
0x026A5C  sub.b  r0l, r0l          ; r0 = b2<<8
0x026A5E  mov.w  r0, e0            ; e0 = b2<<8  ⇒ 高半 ⇒ b2<<24
0x026A60  sub.w  r0, r0
0x026A62  sub.l  er1, er1          ; er1 = 0
0x026A64  mov.b  @(0x3,er6), r1l   ; b3 = payload[2]
0x026A68  mov.w  r1, e1            ; e1 = b3    ⇒ b3<<16
0x026A6A  sub.w  r1, r1
0x026A6C  add.l  er1, er0
0x026A6E  sub.l  er1, er1
0x026A70  mov.b  @(0x4,er6), r1l   ; b4 = payload[3]
0x026A74  shll.l #2, er1  ×4       ; er1 = b4<<8   （4×2 = 8 位，不是 16）
0x026A7C  add.l  er1, er0
0x026A7E  sub.l  er1, er1
0x026A80  mov.b  @(0x5,er6), r1l   ; b5 = payload[4]
0x026A84  add.l  er1, er0
0x026A86  mov.l  er0, @0x400408
```

⇒ **`0x400408 = payload[1]<<24 | payload[2]<<16 | payload[3]<<8 | payload[4]`（32 位大端）**，即下文 §11.4 里被数值门限校验的那个 **V1**。
B3 臂 `0x026B14–0x026B46` 用**逐字节同构**的序列得到同一结果（`0x400408` 与 `0x40040C` 各 4 字节）。

> **H8 语义要点（第三轮新增方法论）**：`MOV.W Rm, ERn` 写 ERn 的**高 16 位**（bits 31:16），低半需显式清。读这族「拼 32 位」代码时，若误按低半读，全部字节序都会错一档。

## 7.5 WRITE BUFFER 地址白名单（`[实证]`）

`0x03ED60` 全镜像**仅 2 处引用**，都在 `0x026534`（CDB `0x3B` handler）：

```asm
0x026702  mov.l #0x0003ED60, er6      ; 表基址
0x026748  add.l #0x0003ED60, er0      ; &table[i] = base + i*8
```

### 校验逻辑

```
地址 = (CDB[3]<<16) | (CDB[4]<<8) | CDB[5]      ← 24 位
长度 = CDB[6..8] 的 24 位字段

入口条件：某字节 != 2 → 状态 0x50；CDB[2] != 0 → 状态 0x50

第 0 组特判：
    addr == 0x00006000 且 addr+len-1 <= 0x0000607F  → 通过
循环 index = 1..4（cmp #5 / bcs）：
    table[i].start <= addr 且 addr <= table[i].end  → 通过
两者都不中 → 状态 0x50
```

表结构：11 组 `(u32 start, u32 end)`。

| 组 | 起 | 止 | 是否校验 |
|---|---|---|---|
| 0 | `0x00006000` | `0x0000607F` | ✓ 特判 |
| 1 | `0x00400000` | `0x0043FFFF` | ✓ 循环 |
| 2 | `0x00800000` | `0x008FFFFF` | ✓ 循环 |
| 3 | `0x00C00000` | `0x00C3FFFF` | ✓ 循环 |
| 4 | `0x00C40000` | `0x00C7FFFF` | ✓ 循环 |
| **5** | **`0x00000000`** | **`0x0007FFFF`** | **✗ 永不匹配** |
| 6–10 | 若干重复项 + `0x00FFDC00` | — | ✗ 不校验 |

### 关键结论：协议层拒绝写引导块

第 5 组正是引导块所在的 512 KB flash 低区，而循环只跑到索引 4，**这一组永远匹配不到**。

物理上引导块与应用区同处一片基址 0 的 AMD flash（`REPORT_MemoryFlash-Map.md`），可写；但 `WRITE BUFFER` 在**协议层刻意拒绝**。

这从另一个角度解释了"为什么升级包不含引导块"——升级路径在设计上就够不到它。

## 7.6 内部命令分派链（`[实证]`，**2026-10-24 第二轮重写**）

> **本节原结论已推翻。** 原文称「`0x03E390`（48 条）→ `0x03EBC0`（26 条）两级内部命令分派」，抽样 16/16 命中。**该前提错误**：`0x03E390` 实为 **85 条**（非 48），第二字段不是 `0x03EBC0` 的索引，而是 `0x01914A` 那张 sense 记录表的索引；`0x03EBC0` 的 26 条也不是内部命令（见 §8.2）。原来的「16/16 命中」是把 `0x03EBC0` 记录首字段（op）恰好等于某些 `field2` 值的巧合当成了索引关系。下文为更正后的结构。

### 7.6.1 真正的两级：状态码 → sense

```
内部状态机（进片 / 校准 / 走片 / 片夹识别 …）
   │  用立即数写入（mov.w #imm 形态）
   ▼
0x400402（低字）/ 0x400404（高字）  ← host_code 载体，16 位
   │  主循环每轮轮询
   ▼
表 0x03E390 —— 每 4 字节 (u16 host_code, u16 sense_index)，85 条，host_code==0 终止
   │  sense_index 取值 0x05–0x8E（143 条表索引用满）
   ▼
表 0x01914A —— 143 条 × 5 字节
   [u8 flags][u8 SenseKey][u8 ASC][u8 ASCQ][u8 vendor]
   │
   ▼
0x011708 REQUEST SENSE 构造器 —— 逐字节把记录字段写进 sense 缓冲
   │
   ▼
主机 CDB 0x03（REQUEST SENSE）取走
```

**关键点：host_code 不是主机下发的命令码，而是固件自产的内部状态码。** 因此 `0x03E390` 与 `0x03E2E8` 不是「两条并列的命令路径」，而是**完全不同的两件事**——前者是状态上报，后者才是命令分派。

### 7.6.2 判决性证据

| 证据 | 地址 | 内容 |
|---|---|---|
| 查表函数唯一入口 | `0x0211B6`–`0x0211D0` | 步长 4 线性搜索 `0x03E390`，`rts` 时 `r0 = *(u16*)(entry+2)`，**原值返回，无移位无掩码** |
| 唯一使用点 | `0x01750E` | `jsr 0x0211B6` → `mulxu.w #0x0005` → `add.l #0x0001914A` → 取 5 字节记录 |
| sense 构造器 | `0x011708` | `mov.w #5,r5 / mulxu.w e4,er5 / add.l #0x01914A,er5`，随后逐字节写 sense 缓冲——**这是「索引→sense」而非「索引→命令」的判决性证据** |
| 写入者 | `0x0275A8` 等多处 | 全部是 `mov.w #imm` 立即数写入，不在 SCSI 分派链上 |

### 7.6.3 闭环校验

校准链（`calib_2753E.md`）记录 `0x1100 → idx 142`，而：

```
rec[142] @0x019410 = 00 02 04 03 07
                     │  │  │  │  └ vendor
                     │  │  │  └─── ASCQ = 0x07
                     │  │  └────── ASC  = 0x04
                     │  └───────── SenseKey = 0x02（NOT READY）
                     └──────────── flags = 0x00
```

即 **NOT READY / 04 / 07 = LOGICAL UNIT NOT READY, INITIALIZING COMMAND REQUIRED**——与「进片未完成」的场合完全吻合。状态码与 sense 码严丝合缝，这条链没有解释余地。

### 7.6.4 与 `0x03EBC0` 的关系：不存在

`0x03E390` 的第二字段（0x05–0x8E）指向 `0x01914A` 的 143 条记录；`0x03EBC0` 的 26 条由引擎 `0x025A56` 独立消费（见 §8.2）。**两者之间没有任何索引关系，「48 ↔ 26」这个映射不存在，落到 `0x03EBC0` 的是 0 条。**

### 7.6.5 两层状态上报：两个输入源、一个出货口（2026-10-24 第三轮更正）

> **第三轮更正**：早前写「两条**彼此独立**的状态码通路」不准确。实测二者**在 `0x400436` 汇合**，该单元实为「统一待刷新 sense 索引」；出货口唯一。

| | 源 A（结果/作业码） | 源 B（解析层/执行层检查码） |
|---|---|---|
| 载体 | `0x400402` / `0x400404` | `0x400436` |
| 取值 | 16 位：`0x1100`/`0x5000`/`0x9000`/`0x0E10`/`0x0E00`/`0x2000`/`0x3000`/`0x0000` | 小值：`0x50`/`0x53`/`0x56` 等 |
| 到 `0x400436` 的路径 | fn `0x021536`：`0x0211B6` 查 `0x03E390` 得 sense_index → `0x02158A` **仅当 `*0x400436==0` 时**写入 | 直接写（`0x50` 三处、`0x53`、`0x56`） |
| 出货 | **两源共用 fn `0x0116A0`**（见下） | 同左 |

**出货链 `[实证]`**（fn `0x0116A0`，由主循环 `0x020EBA` 轮询调用；另一调用点 `0x0114AE`）：

```asm
0x0116A2  mov.w  @0x400436, r6         ; 取原值
0x0116AA  mov.w  r0, @0x400436         ; 读后即清（一次性消费）
0x0116D0  mov.w  #0x0005, r0
0x0116D4  mulxu.w r6, er0              ; 原值 × 5
0x0116D6  mov.b  @(0x1914a,er0), r0l   ; ★ 直接索引 0x01914A，无中间转换表
0x0116C6  mov.w  r6, r1                ; 原值作第二参
0x0116CE  bsr   0x011708               ; 写 sense 缓冲（槽 0x400464 + *0x400503*0x13）
```

`0x011708` 内部同样以原值索引同一张表（`0x011714 mulxu.w e4,er5` + `0x011716 add.l #0x01914A,er5`）。
**⇒ 「索引 = 状态码原值」这条等式在 `0x03E390` 之外的路径上直接坐实**（`0x0116A0` 全镜像仅两个调用点，均在轮询闭环内）。

**旁证**：`0x01914A` 的 `idx 0x50 @0x0192DA = 00 05 24 00 00`（ILLEGAL REQUEST / INVALID FIELD IN CDB）、`idx 0x56 @0x0192F8 = 06 05 2C 00 00`（COMMAND SEQUENCE ERROR）——语义与 `0x50`/`0x56` 的出现场合吻合。

前序「48 条怎么数都凑不齐」，就是因为把两个输入源混在一个表里数。

## 7.7 `0x400408`：E0/C1 参数暂存区（2026-10-24 第四轮更正）

> **第四轮更正**：早前记「全镜像 3 处写、0 处读，推断为引导块消费的请求块」——**两处都错**。
> 引导块已在本地，搜索可证伪：**引导块 64 KB 对 `0x00400408` 的 4 字节立即数与 16 位寻址模式命中均为 0**。

应用侧对 `0x400408` 的全部引用（分类实测）：

| 类别 | 数量 | 位置 |
|---|---|---|
| **直接写**（`mov.w rX,@0x400408`） | **4** | `0x026A88`（C1 臂）、`0x026AC6`（A0 臂）、`0x026B48`（B3 臂）、**`0x028D96`（片夹识别区，此前漏记）** |
| **地址装入**（`mov.l #0x00400408,erN` 当基址用） | 5 | `0x02AEC8`(`er4`)、`0x02B9AA`(`er6`)、`0x02BBC0`(`er5`)、`0x02CACE`(`er5`)、`0x02CB70`(`er4`) |
| **真读**（经寄存器间接） | ≥1 | `0x02BBC6 mov.w @er5,r0`（`er5`=`0x400408`） |

**⇒ 结论**：`0x400408` 是**应用自己的 E0/C1 参数暂存区**（首 4 字节 = 32 位大端 V1，即 §11.4 被数值门限校验的那个量；随后是 V2 与附加字节），由 C1/A0/B3 执行臂写入、由作业处理函数读回（`0x41` 读 `+2` 作目标位置等）。**它与引导块无关**，「交给引导块消费」的推断不成立。

引导块侧的真实分工（见 `_jobfuncsoot_block_code.md`）：应用备好 `0x40033C`（待发 CDB）/ `0x400344`（160B 描述块）/ `0x4003E4`（8B 附加块），引导块的缝隙函数 `0x000192` 用 `EEPMOV.B` 把它们推进 1394 控制器寄存器 `0xFFDC40` / `0xFFDC48` / `0xFFDCE8`。

## 9.2 识别机制

**光学一维条码**，非机械触点。

```
识别函数入口  0x028E30   stm.l er2-er3, @-sp / stm.l er4-er6, @-sp
采集          0x028E4A   jsr 0x02D700（模式 4）
采样缓冲      0xC2D000   10000 × u16 = 63.5 mm @ 4000 dpi
```

`0x028E30` 的唯一调用者是 `0x028BB0`，通过 **`bsr d:16`** 进入（`5c 00 02 7c`，指令 4 字节，目标 = `0x028BB0+4+0x027C`）。

### 自适应阈值 `0x028E5C–0x028E90`

```
遍历 10000 采样求 max / min
if (min > max/2)  min = 0
if (max < 0x0FFF) max = 0x3FFF
threshold = (max + min) >> 1
```

`0x0FFF` / `0x3FFF` 只是钳位常数，**不能据此断言 ADC 位宽**。

## 9.3 两个 bank 的几何

坐标原点是**采样窗口基准端**（缓冲索引 10000 那一端）。

```
pitch_字节 = int(157.480315 × pitch_mm) × 2
base_字节  = (10000 - int(157.480315 × C_mm)) × 2
```

| | 上排 bank `0x80` | 下排 bank `0x81` |
|---|---|---|
| pitch | **10.000 mm** | **8.000 mm** |
| 门控 | 固定 **11.5 mm** | 光学搜索决定 |
| 搜索 | 无 | `1.7–26.0 mm` 内找第一个透光点，命中后 `+2.0 mm` |

## 9.4 位映射 `0x028F8C–0x028FF4`

| 地址 | 语义 | 取值 |
|---|---|---|
| `0x4003FB` | **片夹识别状态/结果码（类型码）** | `0x10–0x1F` + `0x81` |

# 第 10 章 已确认的错误认知（避免下一轮重走）

这一章是本文档最有价值的部分之一。以下每一条都曾被认为是正确的，后来被实测推翻。

## 10.1 固件写的是 `Brownie`，不是 `FH-869`

`REPORT_Holder-Hole-Pattern.md` 把返回码 `0x16/17/18` 直接标成 `FH-869M/S/G`。实测名字表原文是 `Brownie Mount Film` / `Brownie Strip Film` / `Brownie Strip Film with G`。

全镜像**没有出现过 `FH-` 前缀**。`FH-835M` / `FH-869GR` 这些来自主机侧用户文档（Codex 的 `holder-original-text-evidence.json` 已存档原文）。

`Brownie` = 柯达 620 胶卷系列，属中画幅。与 FH-869 系列对应是**合理推断**，但不是固件证据。

## 10.2 `0x400C55` 不是片夹类型码

三份报告有冲突：

| 文档 | 说法 | 判定 |
|---|---|---|
| `REPORT_PhaseM-O_v3.md` §2 | "依 `@0x400C55` 分派 0x40/0x41/0x42/0x80/0x81/0x91，为片夹类型分派" | ✗ 错 |
| `REPORT_MASTER.md` §C | "`0x400C55` 片夹/模式码（源：CDB 0xE0 的 CDB[2]）" | 括号内对，"片夹"一词误导 |
| `REPORT_FilmCode-Mapping.md` §1 | "唯一来源是 SCSI CDB[2]" | ✓ 正确 |

`0x400C55` 存的是 **E0 子功能码**。片夹类型码在 `0x4003FB`（**2026-10-24 更正**，早前此处写 `0x400D79`，见 §9.7 与附录 C 第 3 条）。

连带：`REPORT_HostSide-3.md` §7 待办 2（"片夹码 0x40/41/42/80/81/91 与 LS8000.md3 片夹条目一一对应"）**前提不成立，应撤销**。

`REPORT_FilmCode-Mapping.md` §4 的"片夹族归纳"（`0x40/41/42`→35mm 族，`0x80/81/91/92`→中画幅族）**没有代码依据**，应降级为假设。

## 10.3 线性扫描完全不可用

曾用线性扫描（遇无效字节跳 2 字节）跑出 62,055 条指令、覆盖 186,228 字节——**全部作废**。

原因：它给 `0x1B000–0x1F000` 报了 100% 覆盖，而那里是**全 `0xFF` 的擦除态**。H8 把 `0xFF` 也当合法指令解码。**H8 指令密度太高，线性扫描没有代码/数据区分力。**

`disasm_all.txt` 已回退到引用驱动的干净版本（12,710 条）。

## 10.4 `bsr` 是相对跳转，绝对地址搜不到

`0x028BB0` 处 `5c 00 02 7c` = `bsr 0x028E30`（`BSR d:16`，指令 4 字节）。

对 `0x028E30` 做 3 字节绝对地址搜索得 **0 处**，**不能据此认为无人调用**。凡"某函数 0 引用"的结论，必须同时检查 `bsr`（`0x55` 8 位 / `0x5C` 16 位）可达区。

同理，`cfg_v4.json` 的 `owner` 在 `0x028B00–0x028D00` 是空白，说明该段未被 CFG 覆盖，**不是没有代码**。

## 10.5 覆盖率的分母曾算错

曾报"字节覆盖 27%"，是把数据区（标定表、字符串、浮点表）也算进代码区。按 CFG 口径：

| 指标 | 数值 |
|---|---|
| 函数 | 622 |
| 指令 | 27,215 |
| 越界调用 | **0**（说明 CFG 已收敛，不是截断） |

"0 越界"是关键——它意味着从已知入口可达的代码已全部找到。

## 10.6 H8 的长度模型不可自建

曾用已确认的 11,621 条指令反推 H8 长度模型，只覆盖 106/256 个首字节，扫描结果自相矛盾（"11,256 字节却 16,080 条指令"）。**不要自建，直接用 `h8dis.py` + `h8.lst`。**

## 10.7 sense 码无法用字节模式搜索定位

用主机侧确认的 sense 编码（`70 00 05` / `70 00 06`）去固件里搜，命中 1 处和 4 处，逐处核对**全是指令字节**。

原因：sense 缓冲区运行时构造，不存在静态字节形态。同一根源见 §10.3。

## 10.8 `0x03E518` 不是变长记录

早前报告称"记录非固定长度，id 第二项为 `0x80`"。实测为**定长 12 字节、10 条、第二项是 `0x03`**。

## 10.9 `0x03EB78` 是 271.4，不是 271.6

早前主报告写错，实测 `271.4`。

## 10.10 子 agent 曾写出 17.5 GB 中间文件

某次派出的子 agent 生成 `layout_scan_output.txt` 达 17.5 GB。已删除，磁盘正常。**派活时必须显式限定输出上限。**

## 10.11 `h8.lst` 的 `bt` 其实是 `BRA`（2026-10-24 新增，影响所有分支结论）

`h8.lst` 把 `0x4000` / `0x5800` 编码命名成 `bt`（"branch if true"），但在 H8/300H 上这两个编码是**无条件跳转 `BRA`**。

后果：按「T 置位才跳」读，会把条件判反。`calib_2753E.md` 里 `0x1100` 的判据就是这样被读反的——**`0x0275A4` 的 `cmp.b #0x10` 之后两条分支都汇到同一写点 `0x0275B0`，唯一差别是 `0x400404` 的值**，如果按 `bt` 读会得出完全相反的结论。

**所有 H8 条件分支结论，都该先确认这条指令是真条件跳还是 `BRA`。**

## 10.12 当「验证」看起来特别漂亮时，先怀疑验证方法（2026-10-24 新增）

这是本轮最贵的一条教训。

前序的「两级内部命令分派链」结论，有一条看起来非常硬的验证：**抽样 12 组 host_code，在 `0x03EBC0` 里 12/12 全部命中**。这个命中率足以让人停止怀疑。

实际上三处前提全错：表不是 48 条（是 85）、第二字段不索引 `0x03EBC0`（索引 `0x01914A`）、`0x03EBC0` 不是命令表（是参数块字段描述符）。而那个「12/12 命中」，纯粹是因为 `0x03EBC0` 记录首字段（op）的取值集合与某些 `field2` 值**部分重叠**——被抽中的恰好是重叠的那几个。

**教训**：抽样命中率高，只说明「样本选得有偏」时也会命中率高。判据必须是**判决性指令**（如 `0x011708` 逐字节写 sense 缓冲），而不是「数值对得上」。

## 10.13 两个命名空间「部分重叠」不等于「同一套编号」（2026-10-24 新增）

主机侧 268 个 MAID 能力 ID 与固件 85 个 host_code，精确相同的有 2 个（`0x4000`、`0x1100`）。看起来像「基本对齐、差一点」。

但 16384 和 4356 都是极常见的整数，两个 16 位空间各取 85/268 个值，撞上 2 个纯属偶然。分布也完全不对：md3 以 `0x50`×117、`0x54`×69 为主；host_code 高字节以 `0x08`×44 为首。**「几乎不相交」才是真相，「部分重叠」是噪声。**

判据应该是分布形状，不是交集大小。

## 10.14 `h8tab.py` 的表项正则会整行丢弃 12 位十六进制模式（2026-10-24 第三轮新增，影响全部反汇编）

`h8tab.py` 的表项解析正则是 `^([0-9a-f]{2,8})\s+([0-9a-f]{2,8})\s+…`——**最多只吃 8 位十六进制**。而 `h8.lst` 里有 6 条表项的 val/mask 是 **12 位**（6 字节模式）：

```
01006900  ffffff88  0 mov.l r32ih    r32l
01006980  ffffff88  0 mov.l r32l     r32ih
01006b00  fffffff8  0 mov.l abs16    r32l
01006b20  fffffff8  0 mov.l abs32    r32l
01006b80  fffffff8  0 mov.l r32l     abs16
01006ba0  fffffff8  0 mov.l r32l     abs32
01006d00  ffffff88  0 mov.l r32ph    r32l
01006d80  ffffff88  0 mov.l r32l     pr32h
01006f00  ffffff88  0 mov.l r32d16h  r32l
01006f80  ffffff88  0 mov.l r32l     r32d16h
010078006b20 ffffff0ffff8 0 mov.l r32d32hh r32l    ← 12 位 val/mask
010078006ba0 ffffff0ffff8 0 mov.l r32l    r32d32hh ← 12 位 val/mask
```

这 6 条被**整行跳过**，加载条目数 393 → 399。后果：

| 影响 | 说明 |
|---|---|
| 10 字节指令永不解出 | `mov.l @(d:32,ERn),ERm` / `mov.l ERm,@(d:32,ERn)`（`r32d32hh`）永远匹配失败 |
| 反汇编出现 `.byte` 断点 | A0 处理函数 `0x03A3D4` 两处断点（`0x03A6CE`/`0x03A6E6`），**漏跟 157 条指令**（225 → 382） |
| CFG 损伤有界 | 实测：42 条 10 字节指令未解出，波及 **36/529** 个有归属的函数；因线性扫描按 2 字节步进，**零条错位**（其余指令长度全对），复走后**多解出 1299 条**（36 个函数合计；洞点只有 42 个，但 10 字节指令解开后其后的整段代码才显形） |

带洞函数集中在**图像/扫描数据路径**（`0x2D000–0x34000` 约 20 个），另有 `0x0289B4` 片夹识别主流程、`0x026534` WRITE BUFFER、`0x0267AA` READ BUFFER、`0x02F496` 电机参数（3 洞）。

**教训**：工具链也要审计——「0 越界、CFG 已收敛」这类结论建立在解码器之上，解码器漏表项时，结论照样「看起来收敛」。

## 10.15 「被校验的量是子功能码」是误读（2026-10-24 第三轮新增，lead 自查撤回）

第二轮结论曾写：数值门限比较的对象 `er3` 是 `CDB[1]·256 + CDB[2] + …`，因而推出「`0x91`/`0x92` 恒不可满足 → 死子功能」「有效界是 `CDB[1]` 的 0x20 倍数」。

**根因**：把 `er5` 误当成 CDB 基址。实测函数序言：

```
0x026C06  mov.l #0x0040043c, er4    ; er4 = CDB 基址
0x026C0C  mov.l #0x00000001, er5
0x026C12  add.l sp, er5             ; er5 = sp+1 = payload 暂存区
```

`er5` 是 payload 暂存区，CDB 基址是 `er4`。故 `er3 = payload[1..4]`（32 位 BE 参数 V1），**与 CDB 字节无关**。

**教训**：反汇编里同一函数出现两个基址寄存器（`er4`/`er5`）时，必须先确认**每个**的来源再下结论——一个寄存器的误认会让整条语义链（对象、上限、有效性）全线偏移。判据应是「该指针在函数序言里的初始化」，而不是「它看起来像基址」。

### 11.4.1 被比较的量是 32 位参数 V1 = `payload[1..4]`（不在 CDB 里）

```
0x026C06  mov.l #0x0040043c, er4      ; er4 = CDB 基址
0x026C0C  mov.l #0x00000001, er5
0x026C12  add.l sp, er5               ; er5 = sp+1 = 13 字节 payload 暂存区
0x026CE4–0x026CF6                    ; 清零该暂存区
0x026D06  jsr 0x0118D0                ; 从 data-out 相位把 payload 拷入
0x026D12–0x026D40                    ; er3 = payload[1]<<24 | payload[2]<<16
                                       ;     | payload[3]<<8  | payload[4]
```

**⇒ 六个数值是 32 位大端参数 V1 的上限；V1 与执行层写进 `0x400408` 的那 4 字节同源同序**（C1 臂 `0x026A54`、B3 臂 `0x026B14`，见 §7.4.2）。
**⇒ 这三个数在 data-out payload 里，不在 CDB 里**——想从实机取到它们必须抓 data-out 缓冲，仅抓 CDB 字节流看不到。
**⇒ `0x91`/`0x92` 的 `V1∈{0,1}` 语义自洽**（布尔开关），不是死子功能（第二轮曾误判，见 §10.15）。

自洽性交叉验证：引导块 stock 记录 `@0x6000` 的 V1 = `0x00000085` = 133，落在 B3 的 [−300, 300] 内，目标位 = V1+333 = 466。

### 11.4.2 E0 的 CDB 与 payload 分工（第三轮新增）

| 通道 | 内容 |
|---|---|
| **CDB（10 B，`0x40043C`）** | `[0]=0xE0`；`[1]` 须 `&0x1F==0`（0x20 倍数，`0x026C1A/1E/20`）；**`[2]`=子功能码**（`0x03EDB8` 查表起点 `0x026C5E`）；**`[3..5]` 须为 0**（循环 `0x026C24–0x026C3A` 迭代 **3/4/5**）；`[6..8]`=24 位大端**分配长度**（`0x026C96–0x026CB4`，`CDB[6]` 为高字节）；`[9]`=0（`0x026C3C`） |

# 第 13 章 主机侧（已确认部分）

## 13.1 模块链

```
Nikon Scan.exe
    ↓ LS8000.md3（MAIDEntryPoint / NkMDCtrlEntry）
    ↓ 动态加载 Nkduscan.dll / Nkdsbp2.dll
NkDriverEntry(selector, request, ctx)
    ↓ 内核驱动
SBP-2 over IEEE1394 / USB
    ↓
扫描仪（引导块 → 应用）
```

**「更新器用 selector 5」不准确**（2026-10-24 第二轮更正）：md3 有**三套互不相通的 selector 编号**，第 13 章记录的 `selector 5` 实际属于 `NkDriverEntry`（NKDSBP2.dll），与 `NkCtrlEntry`/`NkMDCtrlEntry` 的 selector 无交集、不可互推。

| 入口 | selector 取值域 | default |
|---|---|---|
| `NkCtrlEntry` | 1..11 + `0x1000` / `0x2000` / `0x2100`（16 位有符号扩展） | 6 |
| `NkMDCtrlEntry` | 1..4（≥5 落 default 返回 `0x1001`） | — |
| `NkDriverEntry` | **1..9**（两 DLL 同构，`add -1; cmp 8; ja`） | — |

另：`NkCtrlEntry` 实际是 **4 参数**（`ret 0x10`，选择子 `movsx ebx,ax`@`0x10091D5C`），与导出名 4×`F` 一致，但与本文档早前「三参」的记录不符。

**调用方向是单向的 md3 → DLL**：md3 造 CDB（~20 个构造器，CDB 在 `[this+8]`，返回长度 6/10），由 `NkDriverEntry` 送上总线。调用点 `0x1009A32A`（加载器虚方法 `0x1009A2E0`，`call [esp+0x1C]`，指针来自 `loader+4`），3 参 `(sel, request, ctx=loader+0x10)`。落地：NKDUSCAN 用 `CreateFileA`+`WriteFile`（USB，`WriteFile`@`0x10002B41`）；NKDSBP2 用 `DeviceIoControl`（`0x10002B66`，**ioctl 码 `0x190012`**）。md3 自身 0 处 `DeviceIoControl`/SCSI 导入。

### 13.1.1 三套 request 结构（§13.1 长期对不上的根因）

| 结构 | 使用者 | 关键偏移 |
|---|---|---|
| md3 导出侧 | `NkCtrlEntry`/`NkMDCtrlEntry` 入参 | `+0x00` 键/长度、`+0x04` 回填/类型、`+0x08` 设备ID/句柄、`+0x0C` 子键/模块码（`"1000"`，`0x1000B237`）；`+0x14`/`+0x18` 只是两个回填槽，**不是** CDB 字段 |
| **传输层** | `NkDriverEntry` 第 2 参 | `+0x00` 设备标识、`+0x04` 标志、`+0x0C` **完成回调**（两 DLL 共 3 处 `call [X+0xC]`）、`+0x14` **CDB 长度**、`+0x18` **CDB 指针**、`+0x1C` 数据长度、`+0x20` 数据指针、`+0x24` 容量 |

传输层结构的决定性证据：`WriteFile(hDev, req[+0x18], req[+0x14], …)`（NKDUSCAN `0x10002B81/88` → 包装器 `0x10002B20` → `WriteFile` `0x10002B41`），以及 NKDSBP2 `0x10002B37-44` 的 `(ptr=+0x20, 0, len=+0x1C)`。

> 即：**本文档早前记的「`request`：`+0x14` CDB 长度…」是传输层结构**，属 `NkDriverEntry`，不是 md3 导出侧那个。两者别混用。

## 15.5 找 `jsr` / `jmp` 的 24 位直接目标

```python
tgt = (0x028E36).to_bytes(3, 'big')     # 3 字节，不是 4
i = 0
while True:
    i = rom.find(tgt, i)
    if i < 0: break
    op = rom[i-1]                        # 0x5E=jsr, 0x5A=jmp
    print(f'0x{0x10000+i-1:06X}  op=0x{op:02X}')
    i += 1
```

**注意 `bsr` 不在此列**：`0x55`（8 位相对）/ `0x5C`（16 位相对）都不编码绝对地址。要检查调用，必须按可达范围扫：

```python
# bsr d:16（0x5C），指令 4 字节，目标 = pc + 4 + s16
for a in range(T-32770, T):
    o = a - 0x10000
    if rom[o] == 0x5C:
        off = int.from_bytes(rom[o+1:o+3], 'big', signed=True)
        if a + 4 + off == T:
            print(f'0x{a:06X} bsr -> 0x{T:06X}')
```
