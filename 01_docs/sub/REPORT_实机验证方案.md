## 0-B. 传输层已核实的关键事实（纯静态，2026-10-24 21:55 补充）

从 `NKDSBP2.dll`（ImageBase `0x10000000`）反汇编得到，这解决了"设备路径与 ioctl 码怎么定"的问题：

### 0-B.1 导出表只有一个函数

```
NKDSBP2.dll 导出:  [0] 0x100041D0  NkDriverEntry
```

所以 `NKDSBP2.dll` 不是给外部直接调用的 API 层，而是被 `LS8000.md3` 通过 `NkDriverEntry` 调用的内部实现。**不能拿它当通用 SCSI 通道用。**

### 0-B.2 真实 ioctl 调用（`0x10002B66`）

```asm
0x10002B55  push   edi                ; &bytesReturned
0x10002B56  push   ebp                ; nOutBufferSize
0x10002B57  push   eax                ; hDevice
0x10002B5C  push   edx                ; lpOutBuffer
0x10002B5D  push   0x2c               ; nInBufferSize = 44
0x10002B5F  push   ebx                ; lpInBuffer
0x10002B60  push   0x190012           ; dwIoControlCode  ★
0x10002B65  push   eax                ; hDevice
0x10002B66  call   dword ptr [0x1000e030]   ; DeviceIoControl
```

**ioctl 码确认为 `0x190012`**，输入结构 **44 字节（`0x2C`）= `SCSI_PASS_THROUGH` 布局**。

解 `0x190012`：`CTL_CODE(0x19, 0x004, METHOD_OUT_DIRECT, FILE_ANY_ACCESS)`〔R24〕
- DeviceType `0x19` = `FILE_DEVICE_SCANNER`
- Function `0x004`（**注意不是 `IOCTL_SCSISCAN_CMD` 的 0x001**）
- Method `METHOD_OUT_DIRECT`，Access `FILE_ANY_ACCESS`〔R24：驱动侧实证 —— 输出侧走 MDL + `MmMapLockedPages` 直写用户页、`Irp->UserBuffer` 访问 0 次，排除 NEITHER；5 个码中只有 `0x19001C` 是 METHOD_BUFFERED〕

即：**Nikon 用的是扫描仪类驱动上的一个厂商自定义 ioctl，结构体却是标准 `SCSI_PASS_THROUGH`。** 这解释了为什么此前用 `IOCTL_SCSISCAN_CMD`（`0x190004`/`0x194004`）打不中。

### 0-B.3 错误处理与重试

### 0-B.4 设备路径是运行时枚举出来的

`LS8000.md3` 的导入表含 `SetupDiGetClassDevsA` / `SetupDiEnumDeviceInfo` / `SetupDiGetDeviceRegistryPropertyA` / `SetupDiClassGuidsFromNameA` / `RegOpenKeyExA`，字符串里有 `'SCSI'` / `'USB'` / `'IEEE1394'` 三个类名。

系统侧已确认的实例（2026-10-24 21:51）：


### 0-B.5 32 位约束（硬约束）

`NKDSBP2.dll` 是 32 位 x86，其 `DeviceIoControl` 走 `FILE_ANY_ACCESS` + 32 位结构体。**从 64 位进程发这个 ioctl 时，结构体里的指针字段必须是 32 位值**——而 64 位进程的用户态指针普遍 > 4 GB，直接传会失败。

可行的宿主：**`C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`（32 位，`[IntPtr]::Size` = 4，已确认存在）**。

> 上面的「已发生的设备接触」小节里那次失败，正是这个 32/64 位问题：Python 是 64 位，`struct.pack_into('<I', ...)` 塞不下 64 位地址。

## 2. 本次静态分析的新发现（直接决定方案可行性）

### 2.1 READ BUFFER 用的是另一张白名单，比 WRITE 宽松得多

固件有**两张**地址白名单，之前只解了一张：

| | 基址 | 条目数 | 内容 |
|---|---|---|---|
| **WRITE** 白名单 | `0x03ED60` | 5 | `0x6000–0x607F`(128 B) / `0x400000–0x43FFFF` / `0x800000–0x8FFFFF` / `0xC00000–0xC3FFFF` / `0xC40000–0xC7FFFF` |
| **READ** 白名单 | `0x03ED88` | 6 | **`0x00000000–0x0007FFFF`** / `0x400000–0x43FFFF` / `0x800000–0x8FFFFF` / `0xC00000–0xC3FFFF` / `0xC40000–0xC7FFFF` / `0x00FFDC00–0x00FFFFFF` |

判决性代码在 READ BUFFER handler `0x0267AA`：

```asm
0x02683E  er0 = idx*8 + 0x0003ed88     ; ★ READ 白名单基址是 0x03ED88，不是 0x03ED60
0x026850  er0 = @er0                    ; start
0x026854  cmp.l er0, er6 ; bcs 下一个   ; offset < start → 换下一条
0x02685A  er0 = @(er1+4)                ; end
0x026860  cmp.l er0, er6 ; bhi 下一个   ; offset > end → 换下一条
0x0268A0  inc.b #1, r4l
0x0268A2  cmp.b #0x06, r4l ; bcs 循环   ; 6 条，穷尽后拒绝
```

**READ 白名单第 0 条就是 `0x00000000–0x0007FFFF`，完整覆盖引导块 `0x0–0xFFFF`，也覆盖应用区 `0x10000–0x47BF8`。** 而 WRITE 侧只开了一个 128 字节的小窗（`0x6000–0x607F`）。这个不对称正是我们需要的：**整片 flash 可读，几乎不可写。**

### 2.2 mode 2 是纯读路径，不碰 flash 解锁

`0x0267BE` 起：`mode = CDB[1] & 0x1F`，只接受 **2** 和 **5**，其余返回状态 `0x50`。

| mode | 路径 | 行为 |
|---|---|---|
| **2** | `0x02682A`→`0x026898` | 查 READ 白名单 → `jsr 0x011900`（flash 读）→ 返回。**纯读，不写任何寄存器** |
| 5 | `0x0268A8`→`0x0268F4` | `offset += 0x60000`，分块拷贝，每轮写 `0x5A00` 到 `0xFFFFBC`（flash 解锁序列） |

**方案只走 mode 2。** mode 5 会动 flash 解锁序列，虽然很可能也只是读，但没必要冒这个险。

### 2.3 长度会被自动裁剪

`0x02687A` 用白名单条目的 end 高 16 位做上界裁剪，所以即使多要了长度也不会越界读到名单外。这意味着**不存在「读过头读到不该读的地方」的风险**——要么被裁到白名单边界，要么直接 `0x50` 拒绝。

## 3. 三级命令序列（附确切 CDB 字节）

### Tier 1 — 纯查询，零物理副作用

| 目的 | CDB（十六进制） | 预期 |
|---|---|---|
| 设备就绪 | `00 00 00 00 00 00` | sense key 0 = 就绪 |
| 身份确认 | `12 00 00 00 24 00` | 36 B，应与镜像 `0x19424`/`0x3E99C` 模板 36/36 一致 |
| 取 sense | `03 00 00 00 FC 00` | 252 B |
| 模式页 | `1A 00 3F 00 FC 00` | 252 B，全部页 |
| **E1 读状态** | 待定（从主机侧构造器 `0x100A0260` 推导） | 应能看到 `0x400402`/`0x400404` 状态字的当前值 |

**Tier 1 的真正价值**：我已经知道固件内部有 85 条状态码和一张 sense 翻译表，但看不到它们随状态变化。E1 读状态能把「内部状态码」与「可观测状态」对应起来，顺便验证我没追完的 `0x400436` 通路。

### Tier 2 — READ BUFFER 只读，目标是引导块

CDB 格式：`3C 02 00 <off[3] 大端> <len[3] 大端> 00`

| 步骤 | CDB | 目的 |
|---|---|---|
| ① 通路自检 | `3C 02 00 00 00 00 00 00 40 00` | 从 offset 0 读 64 B。能通就说明白名单 mode 2 路径可用 |
| ② **应用区对照** | `3C 02 00 00 01 00 00 00 10 00` | 从 `0x10000` 读 4096 B，**与镜像逐字节比对**。这是整条链的校验点：一致才证明读到的就是同一片 flash |
| ③ **引导块转储** | `3C 02 00 00 00 00 00 01 00 00` | 从 `0x0` 读 65536 B = **整个引导块**。若一次传输超限，按 `0x1000` 分 16 次读 |
| ④ 收尾核对 | 读 `0x00FFDC00–0x00FFFFFF` | 白名单第 5 条，可确认高地址区也可读 |

**② 是最重要的一步**，兼具双重作用：**正确性校验**（读回的应用区与镜像一致，才证明读到的就是同一片 flash、offset 无偏移）+ **安全金丝雀**（它是整套流程第一次真正驱动 ASIC/DMA 暂存路径，只读 4 KB；若异常则后面全部停止，引导块根本不碰）。

### Tier 2 风险评估（2026-10-24 21:35 追入）

**调用链已追到底：**

```
READ BUFFER handler 0x0267AA（mode 2 分支）
  0x026898  jsr 0x011900            ; (er0=offset, r1=length)
    → 0x013d98                      ; 薄封装
        0x013DC2  bsr 0x013872      ; 实际暂存拷贝
             0x013890 bsr 0x012bc4  ; 从 offset 拷 length 字节到 0x008DC000
             0x013898 mov.b #0xdc,@0x2000c7   ; ASIC 寄存器
             0x0138A0 mov.b #0x80,@0x2000c2   ; ASIC 寄存器
             0x0138A6 bsr 0x013580 / 0x0135b8 ; DMA 启动
```

**已排除的风险（灾难性后果）：**

| 风险 | 排除依据 |
|---|---|
| **写入 flash** | mode 2 分支**没有任何 flash 写指令**。flash 解锁序列（`mov.w #0x5a00 → @0xffffbc`）只出现在 **mode 5** 分支（`0x0268F4`）。本方案不走 mode 5 |
| **读到白名单外** | offset 先经 `0x03ED88` 六条白名单校验，长度再被条目 end 高 16 位裁剪（`0x02687A`–`0x02687E`）。物理上不可能越界 |
| **缓冲区溢出** | `0x011906 mov.w r1, r4` —— 长度按 **16 位寄存器**取，单次上限 65535 B。要传更大只会被截断 |

**残余风险（小额但真实，必须说明）：这条路径过 ASIC/DMA 暂存引擎，而 DMA 引擎是有状态的。**

`0x013872` 把数据拷到 `0x008DC000`（ASIC 图像缓冲区），再写 ASIC 控制寄存器 `0x2000C7=0xDC`、`0x2000C2=0x80`，最后启动 DMA。若 DMA 引擎处于异常状态（例如上次操作出错后未恢复），这条命令**可能挂住或返回错误**。最坏现实后果是命令超时（SCSI 层可恢复）或 ASIC 进入需复位的瞬态，**不涉及 flash 内容改变**。

诚实记录：`0x0146ea`/`0x0152b0`/`0x015300`/`0x015256`/`0x013608`/`0x013580`/`0x0135b8` 这几个 setup/teardown 子例程我未追完，所以说"零风险"是过度承诺。

**关键旁证：这个例程是通用 helper，不是专用危险路径。** 全镜像统计 `0x011900` 的 `jsr` 调用者共 **14 处**，其中 `0x02182C`（MODE SELECT handler 内）、`0x021D54`（START STOP UNIT 内）、`0x022D86`（SEND DIAGNOSTIC 内）、`0x023A1E`（WRITE(10) 内）、`0x025A42`（参数块校验引擎 `0x025A56` 内）、`0x02724C`（片夹处理代码内）——**全是 NikonScan 正常使用中天天发的普通命令**。READ BUFFER mode 2 调用的不是特殊路径，而是被六类普通命令共用的标准暂存 helper。这大幅降低了"它会把机器搞坏"的可能性。

**缓解措施：** ① 分块读，块长 4096 B（远低于 65535 硬上限，也低于固件 mode 5 自用的 0x8000 块长）；② 金丝雀优先——步骤 ① 只读 64 B、步骤 ② 读 4 KB 并与镜像比对，两步都正常才进 ③；③ 任一步出现非预期 sense 立即停止，不重试、不换参数再试；④ 备好恢复手段（`E0 0x80` reset 与断电重启）；⑤ 不在扫描进行中或刚出错之后做。
