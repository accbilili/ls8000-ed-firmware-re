# Nikon LS-2000 "LS2FW" FIRMDATA 容器格式 (逆向结果)

样本: D:\DS\TEST\LS8000\other\LS200011_512.EXE (194,560 B, PE32 x86, MFC)
资源: 类型 = 字符串 "FIRMDATA", 名 = 整数 128, 语言 = 128
      文件偏移 0x117C0, 大小 92,176 B (0x16810)
      (注意与 LS-8000 升级器不同: 后者是 类型=10 (RCDATA) + 名="FIRMDATA")
产出: LS2000_FIRMDATA.bin (92,176 B) -> LS2000_ROM_decoded.bin (152,992 B)

## 1. 容器格式 (已验证)

    offset  size   内容
    ------  ----   ---------------------------------------------
    0x00    5      ASCII "LS2FW"  魔数
    0x05    1      0x00 (版本/标志)
    0x06    4      u32 **大端** = 压缩块长度 N (样本 = 0x000113CB = 70,603)
    0x0A    6      00 00 00 00 00 00 (保留)
    0x10    N      载荷块 (原样交给解码器):
                      +0x00  4   u32 **小端** = 解压后原始长度 L (样本 = 0x000255A0 = 152,992)
                      +0x04  N-4 自定义 LZSS 压缩流
    0x10+N  剩余   全 0x00 填充 (样本 21,557 B)

  即外层 16 字节头 + 内层 "[u32 LE 原始长度][LZSS]"; 内层结构与 LS-8000
  v1.11 的 FIRMDATA 完全相同, 只是被套在 16 字节 "LS2FW" 头里。

## 2. 压缩算法 (与样本 A 完全相同)

  * 4096 字节环形缓冲, 初值全 0, 写指针 r 从 4096-18 = 4078 (0xFEE) 开始
  * 位读取 LSB-first:  getbuf >>= 1; if not (getbuf & 0x100): getbuf = next_byte() | 0xFF00; 返回 getbuf & 1
  * 标志位 == 1 : 读 1 字节字面量, 输出并写环形缓冲
  * 标志位 == 0 : 读 b1, b2
        pos = b1 | ((b2 & 0xF0) << 4)
        len = (b2 & 0x0F) + 3        (3..18)
        从 ring[(pos+i) & 0xFFF] 逐字节复制
  * 解码器在读取端返回 -1 (块尾) 时停止

## 3. 反汇编证据 (VA, ImageBase = 0x400000, 文件 LS200011_512.EXE)

    0x403E9D  push 0x40D364          ; "FIRMDATA"
    0x403EA2  push 0x80              ; lpName = 128
    0x403EA7  push edi (hInstance)
    0x403EA8  call [0x40A01C]        ; FindResourceA
    0x403EC7  call [0x40A028]        ; SizeofResource
    0x403ECD  cmp  eax, 0x16810      ; 要求资源恰为 92,176 字节
    0x403EF8  cmp  byte [eax],   0x4C   ; 'L'
    0x403EFD  cmp  byte [eax+1], 0x53   ; 'S'
    0x403F03  cmp  byte [eax+2], 0x32   ; '2'
    0x403F09  cmp  byte [eax+3], 0x46   ; 'F'
    0x403F0F  cmp  byte [eax+4], 0x57   ; 'W'
    0x403F25  mov  eax,[esi+0x134]   ; FIRMDATA 指针
    0x403F30  add  eax, 6
    0x403F34  (循环 4 次) shl edx,8 / add edx, byte [eax]   ; => u32 大端 = 70,603
    0x403FD0  mov  eax,[esi+0x134]; add eax,0x10; ...       ; 从偏移 16 起取 N 字节
    0x405E55  (解压入口) fread(&dw,4,1,fp); push dw; call 0x405D57
    0x405D57  LZSS 解码器
    0x405B7A  LZSS 压缩器 (打包升级文件时使用, 由 0x405E8B 分支调用)
    0x405940  初始化 4096 项哈希表 (0x1000 哨兵)
    0x40596F  哈希链插入 (压缩器用)

  重要: LS-8000 的解码函数在 VA 0x405291; LS-2000 中 0x405291 是别的代码,
  真正的解码器在 0x405D57 —— 但两者逐指令同构 (仅内部引用的辅助函数地址不同)。
  另: VA 0x405B94 和 0x405D62 的 mov edi,0xFEE 就是 4078 常量, 是定位锚点。

## 4. 验证 (两条独立判据, 均通过)

    [1] 解出长度     = 152,992 == 头部声明 0x000255A0          通过
    [2] 压缩输入消耗 = 70,599 / 70,599 == N-4                  通过
    内部一致性: 载荷头 u32BE@0x04 (end=0x2D59F) - u32BE@0x08
                (base=0x8000) + 1 = 152,992 == 解出长度        通过
    sha256(LS2000_ROM_decoded.bin) =
        274870fee6fe367a3fa8ea2ac2628a4135f019e8bbe9f4345b586d8adcef5f73

  样本 A 与 B 对比: LS-8000 用 [u32 LE 228345][LZSS]; LS-2000 用 16 字节 LS2FW
  头 + [u32 LE 152992][LZSS]。之前"解出 183,424..184,089 字节"的失败尝试是因为
  没有按头部块长 70,603 截断, 而是从某偏移一直解到整个资源末尾 (溢出到后面的
  零填充 / 越界), 因此长度永远对不上。

## 6. 解出镜像的内容

  镜像覆盖 ROM 地址 0x8000 .. 0x2D59F (载荷头 u32BE@0x08/0x04)。
  载荷头 28 字节:
    0x00 u32BE 0x00010000
    0x04 u32BE 0x0002D59F   <- 结束地址
    0x08 u32BE 0x00008000   <- 起始地址
    0x0C u32BE 0x0000C900
    0x10 12 字节 0D "DF17566" 00 00 48 E4
  随后 0x1C..0x18F 是 62 条 6 字节记录 (u32BE 地址 + u16BE 数据):
    31 条写片内寄存器 0x00FFFF00-0x00FFFFFF
    31 条写 RAM       0x00200000-0x002000FF
  0x190 起是 0xFF 填充(擦除的 flash), 之后是代码/数据; 可读字符串包括
  "Nikon   LS-2000         1.12DF17566" 和 "Nikon   LS-2000-123456  123456"。

  ★ 关于"H8/300H 向量表": **不是**。镜像开头不是向量表 —— 前 16 个 4 字节项
    全部非零, 且镜像根本不覆盖地址 0。镜像区间从 0x8000 开始, 而 H8/300H 的
    异常向量表位于地址 0x000000, 因此**不在本镜像内** (与 LS-8000 一致:
    其镜像从 0x10000 开始, 同样不含引导块/向量表)。
