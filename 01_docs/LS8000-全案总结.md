## 0. 一句话结论

**这是一台 Nikon Super Coolscan 8000 ED 的 H8/300H 固件（应用区 228 KB）+ 三层主机驱动链。镜像已完整解出：20 条 SCSI 命令、12 个 E0 私有子功能、20 张数据表、片夹光学识别全链、机构与换算常数全部落地；主机侧 268 个能力 ID 已分类。**2026-10-24 第三轮更正**：所谓「唯一结构性缺口（引导块 `0x0–0xFFFF` 不可达）」已作废——引导块镜像与全图一直在本地样本里（`LS8000_bootblock.bin` / `LS8000_full_512K.bin`），是文件没被看到，不是硬件限制；E0/C1 两段式结构与 `0x40` 作业处理函数地址也一并更正（见 §4.2 / §11.4）。**

## 2. 镜像与架构（已闭合）

- 头部 28 字节四项算术自洽；**应用从 `0x10000` 开始**，`0x0–0xFFFF` 是引导块。
- **双镜像回退**：段1 入口 `0x10600`，段2 入口 `0x20600`，两段相似度仅 2–6%（不同组件，非副本）。
- 主循环 `0x020B84`（无限循环），每轮 `jsr 0x000192` 一次——这是应用与引导块之间**唯一的**调用缝。
- 622 个已恢复函数中**无 `ldc VBR`/`stc VBR`** → 固件不重定位向量表；在**应用区**检索 256×u32 向量表 0 命中（早前据此断言「引导块不可达」——实为**应用镜像**不含引导块，**引导块镜像本地另有**：`D://DS//TEST//LS8000//LS8000_bootblock.bin` 64 KB）。第三轮已 dump 其向量表：`vec[0]=0x000180`、`vec[2..6]=0x000284`、`vec[7]=0x000280`、`vec[8]=0xFFDC00`。
- L3 实质完成度：控制/机构/sense 主线约 **93%**（第三轮后），**图像算法本体约 75%**（第六轮机制已解：逐行时序 + 采集配置 + 缓冲几何），综合约 **87%**——综合值低于早前估值，因为引导块从「不可达」变成「新开的 0% 分析面」，且**图像算法块同时存在 42 处解码空洞**（见 §12 方法论 10）。

## 4. 命令体系（98%）

### 4.1 SCSI 分派

分派表 `0x03E2E8`，**20 条，记录宽 8 字节** `[u16 code][u16 flags/len][u32 handler]`，`0x03E388` 全零终止；分派器 `0x020E86`（`0x020EFA` 的 `add.l #8` 是步长的直接证据）。

20 条 CDB[0] → 固件 handler 全部定位，其中 INQUIRY `0x023FA4`、READ(10) `0x022EC2`、WRITE BUFFER `0x026534`（固件下载）、E0 `0x026BF8`、E1 `0x026EFC`。

### 4.2 E0 私有命令（12 子功能）

表 `0x03EDB8`，2 字节/条 `[子功能][长度]`，`0xFF` 终止，实测 12 条：

| 子功能 | 长度 | 子功能 | 长度 |
|---|---|---|---|
| `0x40` | 11 | `0x91` | 5 |
| `0x41` | 11 | `0x92` | 5 |
| `0x42` | 11 | `0xA0` | 9 |
| `0x80` | 0 | `0xB0` | 0 |
| `0x81` | 0 | `0xB3` | 13 |
| `0xC1` | 5 | `0xD0` | 0 |

**两段式通路**（第三轮更正：原写「E0 三层」，实为 E0 + C1 两条命令）：

```
主机 ─CDB 0xE0─► 解析层 0x026BF8 ──► 查 0x03EDB8 / 数值门限 / 落存
                  校验 CDB 字节          0x400C55 ← 子功能码
                  CDB[3..5]==0           0x400C56+i ← payload（data-out 相位）
                  CDB[6..8]=分配长度     0x400436 ← 0x50 / 0x53
主机 ─CDB 0xC1─► C1 执行层 0x0269A6 ──► 12 路开关（按 0x400C55）──► 作业层 0x0275F2 ──► 表 0x03EDE8
                  公共尾 0x026BD2          8 臂 + default(0x56)      6 字节/条作业表
                  0x400400←0x4000|子码                                  [键][0][u32 BE 处理函数]
```

- 解析层约束：`CDB[1]&0x1F==0`、**`CDB[3..5]==0`**（第三轮更正，原写 `[3..6]`）、`CDB[9]==0`，`CDB[2]`=子功能码，`CDB[6..8]`=24 位大端**分配长度**，**表内长度 ≤ 分配长度 ≤ 13**。
- **数值门限（第三轮坐实）**：`0x026DF8–0x026EA8` 六条 `cmp.l #imm32,er3`，被比较量是 **V1 = `payload[1..4]`**（32 位 BE）：`0x40`≤15354、`0x41`≤450、`0x42`≤3283、`0xC1`≤450、`0xB3`∈[−300,300]、`0x91/0x92`∈{0,1}；越界 → `0x53` → `0x400436`。
- 作业表 11 条 + `0x00` 终止，键 = 状态字低字节，`jsr` 到处理函数（`0x40→0x2AEAA`、`0x42→0x2CB66`、`0xB3→0x2BBAE`）。**⚠️ 第三轮更正：`0x40` 项原记 `0x2AAAE` 是末两字节错位，真实值为 `0x2AEAA`（表项字节 `00 02 AE AA` @`0x03EDF0`）**。`0x91`/`0x92` 不在这张表里——C1 执行层已内联处理完。

### 4.3 WRITE BUFFER 白名单与升级协议

白名单 `0x03ED60`，11 组 `(u32 start, u32 end)`。**协议层明确拒绝写引导块**——这是补引导块不能靠 SCSI 写的原因。

升级协议：CDB `3B 05 00 00 00 <len24> 00`，数据流帧头 6 字节 `[0xAB][?][len24 大端][0x56]`，净数据 → RAM `0x449B00`；主机送 24 B 版本标记到 `0x400D3D`，与 ROM `0x019448` 逐字节比对，不符拒绝。

### 4.4 `0x400408`：E0/C1 参数暂存区（第四轮更正：既非「只写不读」，也非引导块请求块）

全镜像 **3 处写、0 处读**（C1 `0x026A86`、A0 `0x026AC4`、B3 `0x026B46`）。最自洽解释：**交给引导块消费的请求块**。`[推断]` 强度中等，因为引导块不可见。

## 6. 片夹识别（95%，全链打通）

两阶段机制：`0x0289B4` 主流程 → 读上排 → 若返回 `0x81` → 走片 → 读下排 → `0x028E30` 单排识别。

- `0x81` 是**过程信号**（上排 raw `0x07` 的唯一产出），不是类型码也不是错误码。
- **34.8 mm 的落地形式**：`22.3`@`0x3EF38` × `157.4803149606`@`0x03EDE0`，在 `0x01876A` 截断得 3511，加 `0x07B0` = **5479**（= 34.792 mm）。前序的 3512/5480 各差 1。
- 识别链：采样 → 自适应阈值（`0x028E5C–0x028E90`）→ 定位 → 4 位透光映射（`0x028F8C–0x028FF4`）→ 查表出码（上排 `0x029000`，下排 `0x029052`）。
- 名字表 18 项，**返回码 = 索引 + 0x0F**。
- 失败路径：不重试，置失败码，错误码由上层 `0x02757A–0x0275B0` 合成。

> **本轮修正（重要）**：片夹**类型码落 `0x4003FB`，不是 `0x400D79`**。后者取值只有 0/1，是「识别正常」标志。前序把 `0x028B84` 误记为 `mov.l #0x00400D79,er6`，实为 `mov.b r0l,@0x400D79`。

## 7. 机构、校准与进片流程（本轮补齐）

**进片状态机 `0x027DC4`**（真实范围 `0x027DC4–0x027F22`，CFG 的 `0x027F24` 是下一个函数）：

装载 → 行程闸门 `0x029CD8` → 传感器 `0x02898C` → 预置 4 个标志 → 轮询等走片完成 → 位置累加 → B 轴归零 → 收尾。是**顺序流程 + 单点轮询**，不是 switch 状态机；真正的显式状态机在 `0x0277CE`（`0x420300 ∈ {0,3,4,5}`）。

- **本函数没有软件超时计数器**，唯一时间量是 `0x027E4C` 的 100000，经 `0x02ADCE` 换算成 156250 tick 写硬件定时器。
- 行程上限 = `(0x4202A2 + 12×0x4202EC)` 对 `word@(0x3EE10 + 2×0x4003FB)`；`0x4003FB=0x10` → `0x3EE30 = 0xA410` = **42000**（前序记 42518，差 518）。
- 超时/失败 → `0x400404 ← 0x0E00`（闸门）或 `0x0E10`（传感器）。

**校准链 `0x02753E`**（进片完成 → 可扫描，同一任务内串行）：机构预检 → 稳定 1200 tick → 原位回零两遍 → 位置寄存器预置 `0x07FF` → 等 `0xFFFF54.bit2` → 前端脉冲块 → 条件触发第二轴参考。

**错误码谱系**（8 个结果码 + 7 个状态码）已全列。`0x1100` 的穷举条件是四级闸门缺一不可，其中 `0x4003FB` 只做一次 `cmp.b #0x10`，相等报 `0x1100`、其余 255 个值报 `0`。

> 两处必须记住的更正：① §9.7「`0x400D79` 仍为 1 报 `0x5000`」方向反了，实为 `!=1`；② `0x0110 ≠ 0x1100`，这是历史混淆源。

## 8. 本轮最大成果：17.1 被彻底重写

前序第 17 章把「host_code 语义对齐」列为下一轮首选，逻辑是「主机侧 MAID 能力枚举 ↔ 固件 host_code 逐项比对 → 给 26 条内部命令命名」。**这条路走不通，因为它建在一个错误前提上。**

### 8.1 旧结论错在哪

| 旧结论 | 实际 |
|---|---|
| `0x03E390` 是 48 条主机命令表 | **85 条**，以 `host_code==0` 终止 |
| 第二字段是 `0x03EBC0`（26 条记录）的索引 | 是 `0x01914A` 那张 **5 字节 sense 记录表**的索引 |
| `0x03EBC0` 的 26 条是「内部命令」 | 是 **58 字节参数块的 26 个字段描述符**，由引擎 `0x025A56` 顺序校验，26 个 handler 在全镜像无外部引用 |
| 「48 ↔ 26」存在映射关系 | **不存在**，落到 `0x03EBC0` 的是 0 条 |

旧结论的抽样验证是「16/16 命中」，但那是把 `0x03EBC0` 记录首字段（op）恰好等于某些 `field2` 值的巧合当成了索引关系。

### 8.2 真实结构：host_code 是固件自产的状态码

**host_code 不是主机下发的命令码，而是固件内部状态机写进 `0x400402`（低字）/`0x400404`（高字）的 16 位状态码。** 写入者全部是内部状态机，用 `mov.w #imm` 这类立即数；主循环每轮轮询这两个单元，拿去查 `0x03E390`。

完整通路：

```
内部状态机 ──► 状态码 0x400402/0x400404 ──► 0x0211B6 查 0x03E390（85 条）
                                              │ field2（0x05–0x8E）
                                              ▼
                                    0x01914A 索引 ──► 5 字节记录
                                              ▼
                          [flags][SenseKey][ASC][ASCQ][vendor]
                                              ▼
                              主机 REQUEST SENSE（0x03）取走
```

**判决性证据**：`0x011708` 就是 REQUEST SENSE 构造器——`mov.w #5,r5 / mulxu.w e4,er5 / add.l #0x01914a,er5`，随后逐字节把记录字段写进 sense 缓冲。

**闭环校验**：校准文档记的 `0x1100 → idx142`，而 `rec[142] = 00 02 04 03 07` = **NOT READY / ASC 04 / ASCQ 07 = LOGICAL UNIT NOT READY, INITIALIZING COMMAND REQUIRED**。状态码与 sense 码严丝合缝，这条链没有解释的余地。

### 8.3 主机侧：268 个能力 ID 的分类

| 类 | 数量 | 含义 |
|---|---|---|
| A | **153** | 4 跳内抵达 18 个 CDB 构造点或传输层 |
| B | **115** | 有 vtable、有方法，但 4 跳内不碰 CDB/传输锚点 |
| C | 0 | 未恢复 vtable（534 张 vtable 全恢复） |

- md3 内还有 **5 个「SCSI opcode → CDB 构造器」开关**（`0x100A4DA6`/`0x100A5FFE`/`0x100A67AE`/`0x100A9EA8`/`0x100A516C`），键是 opcode `0x00–0xF8`，**能力 ID 不在这个键空间**。
- **主机完全不做数值范围校验**：对 245,413 条指令扫 9 个约束常量，`cmp/test` 命中 **0**。主机只做子功能码白名单。这意味着越权参数只能靠固件挡。
- 三套 selector 编号互不相通：`NkCtrlEntry` 1..11 + `0x1000/0x2000/0x2100`（实际 4 参数，`ret 0x10`）、`NkMDCtrlEntry` 1..4、`NkDriverEntry` 1..9。
- md3 有**三套互不相通的 request 结构**（导出侧 / `NkDriverEntry` 传输层 / `NkMDCtrlEntry`），这是 §13.1 长期对不上的根因。CDB 最终由 md3 造、`NkDriverEntry` 送上总线（NKDUSCAN 用 `WriteFile`，NKDSBP2 用 `DeviceIoControl`，ioctl `0x190012`）。

### 8.4 对接面的最终答案

> **主机与固件的公共契约只有两样：CDB 字节与 sense 三元组。两侧的命名空间不相交。**

85 个 host_code 与 268 个 cap_id 精确相同**仅 2 个**（`0x4000`、`0x1100`），而 16384/4356 都是常见整数，属巧合。两个命名空间的分布也几乎不相交（md3 以 `0x50`×117、`0x54`×69 为主；host_code 高字节以 `0x08`×44 为首）。

完整链路：

```
主机能力 ID ─► md3 内部按 5 个 opcode 开关翻译成一条 CDB ─► NkDriverEntry 送上总线
                                                                    │
固件: CDB 0x40043C ─► 0x020E86 分派 ─► E0/E1 handler ─► 作业函数
                                                                    │
        状态码 0x400402/0x400404 ◄──────────────────────────────────┘
                │
                ▼
        0x03E390 → 0x01914A → sense 三元组 ─► 主机 REQUEST SENSE
```

从「作业函数」往后，主机无法影响状态码取值。这就是对接面在固件侧的终点。

## 9. 新发现的实质缺陷：`0xD1`

主机确实构造并下发 `0xD1`（构造点 `0x100AA3BC`，调度器 `0x100997A9–0x100997C0` 对 `0xD0–0xD6` 整段放行），但固件**三层全拒**：

1. 解析表 `0x03EDB8` 12 条无 `0xD1` → 状态 `0x50`
2. C1 执行层 `0x0269A6` 12 路开关无 `0xD1` 臂 → default → 状态 `0x56`
3. 作业表 `0x03EDE8` 无 `0xD1` 键 → 落到 `0x00` 终止记录

又因为主机不做数值校验，这个错配一路直达总线，只能靠固件在解析层挡掉。要么主机照抄了一份过期的私有命令清单，要么 `0xD1` 属于另一台机型的能力。

## 10. 两层状态上报：前序混乱的根源

固件有**两条状态码通路，但它们不是「彼此独立」**（第三轮更正）：两个输入源在 `0x400436` 汇合，出货口唯一 = fn `0x0116A0`（读原值→清零→×5→**直索引 `0x01914A`**→写 sense 缓冲）。详见 REPORT §7.6.5。

| | 通路 A（结果/作业码） | 通路 B（解析层检查码） |
|---|---|---|
| 载体 | `0x400402` / `0x400404` | `0x400436` |
| 取值 | 16 位：`0x1100`/`0x5000`/`0x9000`/`0x0E10`/`0x2000`/`0x3000`/`0x0000` | 小值：`0x50`/`0x56` |

## 12. 方法论与坑（避免下一轮重走）

1. **`h8.lst` 把 `0x4000`/`0x5800` 命名成 `bt`，实为 `BRA`。** 按「T 置位才跳」读，会把 `0x1100` 的判据读反。所有 H8 分支结论都该先过这一遍。
2. **`bsr` 是相对跳转，绝对地址搜不到**，必须按可达区扫描。
3. **H8/300H 大端**，多字节表和 `mov.l` 立即数都按大端读。
4. **线性扫描完全不可用**，必须按函数序言（`stm.l` / `mov.l erN,@-sp`）定起点。
5. `cfg_v4.json` 有两大空白段：`0x025A56–0x026534`、`0x028B00–0x028E68`。涉及这两段必须自建反汇编。
6. 覆盖率的分母曾算错——`.text` 不是全代码，还有 RAM 驻留副本。
7. sense 码无法用字节模式搜索定位，只能顺 `0x011708` 这类构造器反推。
8. **子 agent 曾写出 17.5 GB 中间文件**——派子任务时必须明确「单文件 ≤2 MB」「禁止写入 `D:\`」。
9. 后台模式（`run_in_background`）的子任务约 2 分钟后被系统回收，会静默变成 `killed`；要跑长任务必须前台并行。
10. **（第三轮）`h8tab.py` 的表项正则 `[0-9a-f]{2,8}` 装不下 12 位十六进制** → h8.lst 里 6 条 6 字节模式表项被整行丢弃（393→399 条），`mov.l @(d:32,ERn),ERm` 等 10 字节指令**永不解出** → 反汇编出现 `.byte` 断点并漏跟后续代码。实测损伤：42 条未解出、波及 36/529 个函数、**零错位**，**复走后多解出 1299 条不可见指令**（洞点仅 42 个，但 10 字节指令解开后其后整段代码才显形）。修复：`03_analysisirmware\_jobfuncs\h8fix.py`（只重解析，不改 `D://`）。**工具链也要审计**——「0 越界、CFG 已收敛」是建立在解码器之上的结论。
11. **（第三轮）`MOV.W Rm, ERn` 写 ERn 的高 16 位**（bits 31:16），低半需显式清；读「拼 32 位」代码时误按低半读会让全部字节序错一档。
12. **（第三轮）同一函数里两个基址寄存器必须逐个确认来源**：`0x026BF8` 里 `er4` 才是 CDB 基址、`er5` 是 payload 暂存区；误认会让语义链全线偏移（本轮已因此撤回一次自身结论，见 REPORT §10.15）。
13. **（第三轮）列目录会截断**（补 M14：**工具链也要审计**——「0 越界、CFG 已收敛」这类结论是建立在解码器之上的，解码器丢表项时结论照样「看起来收敛」；实测损伤 42 条 10 字节指令未解出、波及 36/529 个函数、复走后**多解出 1299 条**）
14. **（第六轮）`MOV.W Rm, ERn` 写 ERn 的高 16 位**（bits 31:16）——误按低半读会让全部 32 位组装的字节序错一档
15. **（第六轮）同一函数里两个基址寄存器要逐个确认来源**（`0x026BF8` 里 `er4`=CDB 基址、`er5`=payload 暂存区；误认会让语义链全线偏移）
16. **（第六轮）`0x74` 之类的常量先看它怎么用**——`0x74 + sp` 是**栈帧偏移**，不是「116 字节行距」
17. **（第三轮）列目录会截断**：`ls | head -30` 导致 `LS8000_bootblock.bin` / `LS8000_full_512K.bin` 长期未被发现，进而把「样本固有限制」当结论。**断言「某文件不存在」前必须用完整路径直接验证。**
