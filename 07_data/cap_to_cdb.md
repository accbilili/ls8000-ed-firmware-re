# 268 个能力 ID 到 CDB 的对接面定案（17.1 重定）

日期：2026-10-24 · 输入 `LS8000.md3`（PE32，ImageBase `0x10000000`，`.text` VA `0x10001000`）
方法：全 `.text` 递归下降 CFG + 534 张 vtable 恢复 + 从 ctor 与 vtable 全槽做 4 跳正向可达性判定
分级：`[实证]` 可复现；`[推断]` 自洽未直证；`[未证]` 仅线索

---

## 0. 结论摘要

1. **268 个能力 ID 全部落到 CDB 构造器或本地虚表对象上，没有一个是空壳**（C 类 = 0，因为 534 张 vtable 全恢复，每个 ID 都能拿到方法集）。其中 **A 类（会碰 CDB / 传输层）153 个，B 类（纯本地）115 个**。
2. **主机与固件的对接面就是 CDB 本身**，不是 `host_code`、不是能力 ID、也不是 selector 编号。三条独立证据：host_code 是固件自产状态码（`hostcode_source.md`）；85 个 host_code 在 md3 里只有 2 个与 cap_id 精确相同（§5）；CDB 由 md3 造、`NkDriverEntry` 送上总线（`exports.md`）。
3. **主机不做数值范围校验**：对 245,413 条已确认对齐的指令扫固件侧 9 个约束常量（`0x3BFA`/15354、`0x1C2`/450、`0xCD3`/3283、`0x12C`/300、`0xFED4`/−300 等），`cmp/test` 命中 **0 条**。主机只做子功能码**白名单**。
4. **17.1 节「把主机侧能力枚举与 48/85 条 host_code 对齐」这条路线作废**，见 §5。

## 1. 方法与覆盖边界（先说清楚能证到什么程度）

- CFG：以 md3 全 `.text` 递归下降 + 跳转表解析，得 **22,272 函数 / 239,689 指令 / 7,404 条直调边**（`_g3/g3cfg.pkl`）。旧 CFG 未解析 `.text` 内 `FF 24 /4` 跳转表，本轮已重扫——这也是本轮能发现 §3 那 5 个开关的原因。
- vtable：534 张，以「ctor 写入某全局地址」为基址、截断到下一基址。命令类对象 20 张 vtable 实测均为 **10 槽**，前 9 槽是同一组基类方法，**槽 9（`+0x24`）= BuildCDB** `[实证]`。
- 判定锚点共 **73 个**：`cdb_sites.json` 的 18 个 BuildCDB 函数 + 21 个 CDB 构造器 + 3 张传输层 vtable（`0x100C25D0`/`0x100C2620`/`0x100C2660`）展开的 31 个槽 + 子功能白名单/分派函数 3 个（`0x100A1EC0`/`0x100AA1D0`/`0x100A42E0`）。
- 对每个 cap：以 `ctor + vtable 全部槽` 为种子集做 4 跳正向 BFS，与 73 锚点求交。
  - 命中 → A 类
  - 恢复了 vtable 但 4 跳未命中 → B 类
  - 未恢复任何方法 → C 类（本轮 0 条）
- **覆盖边界**：B 类不是动态全路径证明。C++ 虚调用若指向他对象（非本 cap 的 vtable），静态仍无法展开，可能漏掉一条通往 CDB 的边。因此「A 类 153」是**下界**，「B 类 115」是**上界**。

## 3. md3 内部还有 5 个「SCSI opcode → CDB 构造器」开关 `[实证]`

这解释了 18 条 CDB 之外，md3 为什么还能构造标准命令：

| 开关 | 站点 VA | 上界 | 键 | 臂 |
|---|---|---|---|---|
| S1 | `0x100A4DA6` | `0x28` | SCSI opcode | CDB 构造函数 |
| S2 | `0x100A5FFE` | `0xE1` | SCSI opcode | CDB 构造函数 |
| S3 | `0x100A67AE` | `0xE1` | SCSI opcode | CDB 构造函数 |
| S4 | `0x100A9EA8` | `0x2A` | SCSI opcode | CDB 构造函数 |
| S5 | `0x100A516C` | `0xF8` | SCSI opcode（含 `C8/C9/CA/CB/D1/E1/E2/F0/F1/F2/F8`） | CDB 构造函数 |

键全部是 **SCSI opcode**（`0x00`–`0xF8`），臂是构造函数。即 md3 侧的第二层分派是按标准 opcode 走，而**能力 ID 那 268 个编号不在这个键空间里**。两条分派链在 md3 内部并行，彼此不换算。

## 4. 主机对参数不做范围校验 `[实证]`

扫描范围：`_g3/g3cfg.pkl` 中已确认对齐的 **245,413 条指令**，目标常量 9 个：

| 固件约束 | 常量 | md3 `cmp/test` 命中 | md3 `push` 命中 |
|---|---|---|---|
| `0x40` ≤ 15354 | `0x3BFA` | **0** | 0 |
| `0x41` ≤ 450 | `0x1C2` | **0** | 3（`0x1C1`=449，见下） |
| `0x42` ≤ 3283 | `0xCD3` | **0** | 0 |
| `0xC1` ≤ 450 | `0x1C2` | **0** | 同上 3 |
| `0xB3` ∈ [−300,300] | `0x12C` / `0x12B` / `0xFED4` | **0** | 5（`0x12C`=300 ×3、`0x12B`=299 ×2） |

`push` 命中集中在 `0x10078200/0x1007822F`（`0x12C`）、`0x1009615D/0x10096187`、`0x100A5DAA/0x100A5DBB`、`0x100A8AA6/0x100A8AC7`、`0x1005794E`/`0x10063744`（`0x1C1`）。这些是**参数装载而非边界比较**（`cmp` 命中数为 0 是硬判据）。

值得注意的是 `0x1C1 = 449 = 450 − 1`、`0x12C = 300` 恰好是 `0xB3` 的上界——数值上与固件约束对得上，但**形态是 push 不是 cmp**，所以只能记为 `[推断]`：主机按固定容量给缓冲区留量，把范围校验完全甩给固件。**这条不对称意味着：主机侧越权参数不会被 md3 拦截，只能靠固件 `0x03EDB8` 表返回 ILLEGAL REQUEST。**

## 5. 与固件 host_code 的关系：命名空间不相交 `[实证]`

（依据 `hostcode_source.md` §5 的独立反例检查，本节复述其结论并接上本任务的分类）

- 85 个 `host_code` 里，作为 x86 立即数在 md3 `.text` 出现的 **20 个**，其中可判别的 13 个（如 `0x0930` @`0x10052C65 push 0x930`）。
- 与 268 个 `cap_id` **精确相同的只有 2 个**：`0x4000`（cap `0x40/0x00`，handler `0x1004BC10`）、`0x1100`（cap `0x11/0x00`，handler `0x10064380`）。而 16384、4356 都是常见整数，属巧合。
- 两个命名空间的分布也几乎不相交：md3 group 以 `0x50`×117、`0x54`×69、`0x60`×29 为主；固件 host_code 高字节以 `0x08`×44 为首。

**结论：md3 不能构造这 85 个码。** 因为 `hostcode_source.md` 已实证这 85 个码是固件内部状态机用立即数写入 `0x400402`/`0x400404` 的，主循环轮询后查 `0x03E390`，最终经 `0x01914A` 翻译成 sense 三元组（`[flags][SenseKey][ASC][ASCQ][vendor]`）供主机 `REQUEST SENSE` 取走。

## 6. 对接面定论（写 17.1 用）

主机侧往下的出口是**三层，且互不换算**：

| 层 | 载体 | 编号空间 | 覆盖 |
|---|---|---|---|
| 出口 1（主） | **SCSI CDB**（标准 opcode + E0/E1 私有） | opcode `0x00`–`0xF8` | A 类 153 个能力 ID；18 条已定案构造点 + 5 个 opcode 开关 |
| 出口 2 | `NkDriverEntry(selector, request, ctx)` | selector **1..9** | 由 md3 装载器虚方法 `0x1009A2E0` 调 `0x1009A32A` 发出 |
| 出口 3 | `NkCtrlEntry(selector, …)` / `NkMDCtrlEntry` | selector 1..11 / 1..4 | 设备对象虚方法，`NkCtrlEntry` 实际 4 参数 |

状态回流是**单向的另一条路**：固件 → 内部状态码 → `0x03E390` → `0x01914A` → sense 三元组 → 主机 `REQUEST SENSE`。

**因此 17.1 的正确写法不是「主机命令表 ↔ 固件命令表对齐」，而是：**
> 主机下发能力 ID → md3 内部按 5 个 opcode 开关把请求翻译成一条 CDB → `NkDriverEntry` 送上总线 → 固件执行并把进展写成内部状态码 → 主循环把状态码翻成 sense 三元组 → 主机 `REQUEST SENSE` 取回。两侧的命令编号与状态编号**各自独立、无换算关系**，唯一的公共契约是 CDB 字节与 sense 三元组。

## 7. 未解决的疑问

1. B 类 115 个是否真的没有一个能抵达 CDB——需动态跟踪或补全他对象虚调用解析。
2. `0x1C1`(449)/`0x12C`(300) 的 `push` 装载点（如 `0x100A5DAA`）与固件约束的对应关系，是容量巧合还是有心留量。
3. `REQUEST SENSE(0x03)` 在 md3 内未构造（`cdb_sites.md`），sense 到底由谁发起——疑在 NKDUSCAN 的 autosense 路径，待查。
4. `0xD1` 主机确实发出、固件已定位为 idx `0x50` / ILLEGAL REQUEST `05 24 00`（见 `e0_bridge.md`），但**主机为何仍要发一个固件必然拒绝的子功能**，尚未解释。
