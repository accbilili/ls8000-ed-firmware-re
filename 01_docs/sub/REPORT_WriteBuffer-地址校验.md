# WRITE BUFFER 地址白名单校验恢复（0x03ED60 的真实用途）

日期：2026-10-24
输入：`cfg_v4.json`（27,215 指令）+ `LS8000_111_ROM.bin`
边界：纯静态

---

## 1. 引用确认

`0x03ED60` 全镜像仅两处引用，都在 `0x026534`（WRITE BUFFER / CDB `0x3B` handler）：

```asm
0x026702  mov.l #0x0003ed60,er6    ; 表基址
0x026748  add.l #0x0003ed60,er0    ; 表项 = base + index*8
```

**因此 `0x03ED60` 是 WRITE BUFFER 专用的地址合法性白名单，不是 READ BUFFER 的。**（此前 `REPORT_DataTables-解析.md` §4 的推断需要收窄。）

## 2. 校验逻辑（0x0266D0–0x02679A）

### 2.1 取地址与长度

```asm
0x0266D2  r4l = CDB[3]
0x0266DC  r0l = CDB[4]
0x0266E0  er0 <<= 16                 ; (×4 四次)
0x0266E8  er4 += er0
0x0266EC  r0l = CDB[5]
0x0266F0  er4 += er0                 ; er4 = (CDB[3]<<16)|(CDB[4]<<8)|CDB[5]  ← 24 位地址
```

`er3` 为数据长度（来自 CDB[6..8] 的 24 位字段，Harness 已确认）。

### 2.2 入口条件

```asm
0x0266F4  cmp.b #0x02,r0l ; bne 0x026794   ; 某字节 != 2 → 状态 0x50
0x0266FA  r0l = CDB[2]    ; bne 0x02678C   ; CDB[2] != 0 → 状态 0x50
```

### 2.3 第 0 组：特判

```asm
0x026702  er6 = &0x03ED60
0x026708  er0 = table[0].start        ; 0x00006000
0x02670C  cmp er0, er4 ; bne search
0x026710  er0 = er4 + er3 - 1         ; 结束地址
0x026716  er1 = table[0].end          ; 0x0000607F
0x02671C  cmp er1, er0 ; bhi search
0x026720  … 校验通过 → jsr 0x0118d0 / bsr 0x02726E
```

### 2.4 第 1–4 组：循环搜索

```asm
0x026732  er6 = 1
0x02673E  er2 = er4 + er3 - 1          ; 结束地址
0x026742  er0 = er6 * 8
0x026748  er0 += 0x03ED60              ; &table[er6]
0x026750  er0 = table[er6].start
0x026754  cmp er0, er4 ; bcs next      ; 地址 < start → 下一项
0x026758  er0 = &table[er6] + 4
0x02675C  er0 = table[er6].end
0x026760  cmp er0, er4 ; bhi next      ; 地址 > end → 下一项
0x026764  … 命中
0x026782  er6++
0x026784  cmp er6, 5
0x02678A  bcs 0x026742
0x02678C  mov.w #0x0050,r0 ; mov.w r0,@er5   ; 校验失败 → 状态 0x50
```

**循环只覆盖索引 1–4（`er6 < 5`），加上特判的第 0 组，共校验 5 组。**

## 3. 实际生效的白名单范围

| 组 | 起 | 止 | 大小 | 是否被校验 |
|---|---|---|---|---|
| 0 | `0x00006000` | `0x0000607F` | 128 B | ✓（特判） |
| 1 | `0x00400000` | `0x0043FFFF` | 256 KB | ✓（循环） |
| 2 | `0x00800000` | `0x008FFFFF` | 1 MB | ✓（循环） |
| 3 | `0x00C00000` | `0x00C3FFFF` | 256 KB | ✓（循环） |
| 4 | `0x00C40000` | `0x00C7FFFF` | 256 KB | ✓（循环） |
| 5 | `0x00000000` | `0x0007FFFF` | 512 KB | **✗ 不校验** |
| 6–10 | `0x400000`…`0xFFDC00` | — | — | **✗ 不校验** |

### 3.1 关键结论：引导块 flash 不在写白名单内

表里第 5 组正是**引导块所在的 `0x000000–0x0007FFFF`（512 KB flash 低区）**，而循环只跑到索引 4，**这一组永远不会被匹配到**。

因此：**WRITE BUFFER 无法写入引导块**。这是一个刻意的写入边界——固件把更新范围限制在主 RAM、ASIC 图像存储与 `0xC` 段，不允许通过升级协议改写引导块/向量表。

这与 `REPORT_MemoryFlash-Map.md` 的结论（引导块与应用区同处一片基址 0 的 AMD flash）并不矛盾：物理上可写，但协议层拒绝。

### 3.2 后 6 组的归属未定

索引 5–10 的 6 组（含 `0x000000`、`0xFFDC00` 及若干重复项）在 WRITE BUFFER 中不生效。可能是：
- 供 READ BUFFER 或其它 handler 使用的同一张表尾部（但未找到 `0x03ED60` 的其它引用）
- 供引导块（不在镜像内）使用的表
- 历史遗留/冗余项

**未确认，不做断言。**

## 4. `0x400408` 的消费方：只写不读

全镜像扫描 `0x400408`：**3 处写入，0 处读取**。

| 地址 | 所属 | 分支 |
|---|---|---|
| `0x026A86` | `0x0269A6` | `0xC1` 子功能 |
| `0x026AC4` | `0x0269A6` | `0xA0` 子功能 |
| `0x026B46` | `0x0269A6` | `0xB3` 子功能 |

三者都在写 24 位值到同一地址，但**镜像内没有任何代码读取它**。

同时扫描 `0x400400–0x40042F` 整个区间，被访问的字段是：`0x400400 / 0x400402 / 0x400404 / 0x400406 / 0x400416 / 0x40041C / 0x400426 / 0x40042E`——**`0x400408 / 0x40040A / 0x40040C / 0x400412–0x400414` 均无读取方**。

**合理解释**：`0x400408` 起是**交给引导块（`0x0–0xFFFF`）消费的请求块**。引导块负责实际的设备 I/O（含 1394 收发 ISR），它读取应用层写入的地址/参数后执行。这与以下事实一致：

- 应用每轮主循环只 `jsr 0x000192` 一次（Harness 已确认，引导块唯一入口）
- 应用无法直接触碰的部分（向量表、ISR、CDB 落地 `0x40043C` 的代码）都在引导块内

**推断强度**：中等。这是目前最自洽的解释，但引导块不可见，无法直接验证。
