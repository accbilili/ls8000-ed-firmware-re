# `0x03E390` 第二字段定案：它不是 `0x03EBC0` 的索引

日期：2026-10-24 · 输入：`LS8000_111_ROM.bin`（地址 = 文件偏移 + `0x10000`）、`cfg_v4.json`
方法：整段字节 dump + 全镜像立即数引用扫描 + 反汇编判决性指令
边界：纯静态，未执行任何命令

---

## 0. 结论（一句话）

**第二字段是一个 `u16` 代码（code），它是 `0x01914A` 那张 5 字节定长记录表的索引，不是 `0x03EBC0` 的字节偏移、也不是条目号。**
`0x03E390` 表实为 **85 条**（不是 48 条），以 `host_code == 0x0000` 终止；`field2 == 0` 是"未命中"返回值，正好指向 `0x01914A` 的第 0 条全零记录。

三处独立证据：

| 证据 | 地址 | 内容 |
|---|---|---|
| 查表函数唯一入口 | `0x0211B6`–`0x0211D0` | 步长 4 线性搜索 `0x03E390`，`rts` 时 `r0 = *(u16*)(entry+2)`，**原值返回，无移位无掩码** |
| 唯一使用点 | `0x01750E`–`0x017526` | `jsr 0x0211B6` → `mulxu.w #0x0005` → `add.l #0x0001914A` → 取记录 |
| 健壮性上界 | `0x01914A`+`0x8E*5` = `0x019410` | 全表 143 条（`0x00`–`0x8E`），`0x019415` 已是构建信息串；`field2` 实测最小 `0x05`、最大 `0x8E`，**正好用满** |

`0x03EBC0` 的 26 条记录**不是**按编号索引的表，而是被 `0x025A56` 顺序执行的"微操作链"（见 §4）。因此「48 ↔ 26」这个关系**不存在**：48 条里落到 `0x03EBC0` 的是 **0 条**。前序"抽样 16/16 命中"是把 `0x03EBC0` 记录首字段（`op`）恰好等于某些 `field2` 值的巧合当成了索引关系——那些被抽中的 16 条，正是 `field2 ∈ {0x0E,0x12,0x19,0x1A,0x20,0x28,0x29,0x2C,0x2D,0x2E,0x32,...}` 的条目（`0x03EBC0` 的 `op` 集合与它们部分重叠）。

## 2. 判决性指令

### 2.1 `0x0211B6` — 查表函数（全镜像唯一的 `0x03E390` 引用）

```asm
0x0211B6  mov.w     r0, e0            ; e0 = 入参 host_code
0x0211B8  mov.l     #0x0003e390, er1  ; er1 = 表基址
0x0211BE  bt        0x0211c8
0x0211C0  mov.w     @er1, r0          ; r0 = entry.host_code
0x0211C2  cmp.w     e0, r0
0x0211C4  beq       0x0211cc          ; 命中
0x0211C6  adds.l    #4, er1           ; ← 步长 4，字节
0x0211C8  mov.w     @er1, r0
0x0211CA  bne       0x0211c0          ; host_code != 0 继续
0x0211CC  mov.w     @(0x2,er1), r0    ; ← 返回值 = 第二字段，原值
0x0211D0  rts
```

**这是"不经任何加工"的直接返回**：没有 `shl`、没有 `and`、没有 `*5`。所以第二字段本身是个**值**，不是"偏移/索引的编码形式"。

调用点（全镜像 7 处，`cfg_v4.json` 扫 `0x211b6`）：`0x01750E`、`0x0175B8`（`0x0174BC`）、`0x0215FE`、`0x0216D6`（`0x02159C` TEST UNIT READY）、`0x021728`（`0x021708`）、`0x022FC0`、`0x02381E`（`0x022F4E`）。

### 2.2 `0x01750E` — 把返回值当索引使用（判决书）

```asm
0x01750C  mov.w     e5, r0            ; r0 = host_code（第 2 个实参）
0x01750E  jsr       0x0211b6          ; r0 = field2
0x017512  mov.w     r0, @(0xfff4,er6)
0x017516  mov.w     @(0xfff4,er6), r0
0x01751A  mov.w     #0x0005, e0
0x01751E  mulxu.w   e0, er0           ; ← field2 * 5
0x017520  add.l     #0x0001914a, er0  ; ← + 0x01914A  = 记录地址
0x017526  mov.l     er0, @(0xfff6,er6)
0x01752C  mov.l     @(0xfff6,er6), er0
0x017532  mov.b     @er0, r0l          ; b0 = flags
0x01753C  extu.w    r0
0x01753E  btst      #7, r0l            ; bit7=1 → 丢弃
0x017540  bne       0x017594
0x017548  btst      #1, r0l            ; bit1=0 → 丢弃
0x01754A  beq       0x017594
0x017552  mov.b     @(0x1,er0), r0l ; → 0x449AF1
0x017562  mov.b     @(0x2,er0), r0l ; → 0x449AF2
0x017572  mov.b     @(0x3,er0), r0l ; → 0x449AF3
0x017582  mov.b     @(0x4,er0), r0l ; → 0x449AF4
```

第二条等价路径（`0x0175B8`→`0x0175CA`）对第 1 个实参重复同一动作。`0x0116D6` / `0x011716` / `0x022B0A` / `0x022C0C` 也是同一算式（`#5` 乘法 + `0x01914A`），四路互相独立。

### 2.3 `0x01914A` 表规模自证

```
rec[0]  0x01914A: 00 00 00 00 00          ← 未命中码 0 的"空记录"
rec[0x8E] 0x019410: 00 02 04 03 07        ← field2 最大值对应的记录
0x019415: FF 80 20 21 22 …                ← 已进入构建信息块，不是记录
```
143 条 × 5 字节 = 715 字节，`0x01914A + 715 = 0x019415`，与下一个结构的起点**字节级吻合**。

### 2.4 记录结构（`0x01914A + n*5`）

`[b0 flags][b1][b2][b3][b4]`。`b0` 的位用法来自三个独立消费者：

| 位 | 检查点 | 作用 |
|---|---|---|
| bit7 | `0x01753E` | 1 → 记录作废（`0x01914A` 中 `0x01`/`0x02`/`0x03` 三条为 `C0`/`80`/`80`） |
| bit6 | `0x0116DE` | 1 → 跳过 `0x011882` 分支 |
| bit5 | `0x011724` | 1 → 写入 `0xF0` 前缀字节 |
| bit1 | `0x017548` | 1 → 拷贝 `b1..b4` 到 `0x449AF1..0x449AF4` |

`b1..b4` 的去向：`0x016F46` 把它们作为**状态响应块**（首字节 `0xAA`）的偏移 `0x12`–`0x15` 输出。`[b1b2]` 可读作一个 `u16` "kind"（`0x0161`/`0x0204`/`0x023A`/`0x0311`/`0x0403`/`0x0408`/`0x0411`/`0x0415`/`0x0444`/`0x0453`/`0x0460`/`0x0462`，共 12 种），`[b3][b4]` 是两个小索引/模式字节。**这个 2+1+1 切分是 `[推断]`，字节本身是 `[实证]`。**

## 3. 五个假设逐个检验

| 假设 | 判据 | 结论 |
|---|---|---|
| **H1** `0x03EBC0` 字节偏移 | `0x03EBC0` 全镜像**只有 1 处引用**（`0x025A72`），该处是 `mov.l #0x0003ebc0, er6` 后接 `add.l #0x10` 步进循环，**没有任何"基址 + 变址"的算式**；且 `0x0211CC` 返回值未经移位。`0x03EBC0+0x10` = 0x03EBD0 = 第 1 条记录的 `lo` 字段（`0x00000000`），不是条目首，`0x03EBC0+0x05` 落在 `len` 字段中间 | **否** |
| **H2** 条目号 | 26 条上限 0x19；实测 `field2` 上到 `0x8E`，且 `0x1A..0x1E`/`0x20..0x37` 若当条目号会落进第 1–3 条记录；即使允许，`0x7E`/`0x8B` 也越界。**表本身不更长**：`0x03EBC0+26*16 = 0x03ED60`，紧接白名单第 0 组 `(0x00006000,0x0000607F)`，无第二条表紧随其后 | **否** |
| **H3** 另一张表的索引 | `0x01751E` 的 `mulxu.w #5` + `add.l #0x01914A` 是显式算式；表长 143、`field2` 值域 `0x05..0x8E` 恰好落在 0–142；8 处消费点同一算式 | **成立（正解）** |
| **H4** 两个 u8（高=子表号，低=条目号） | `field2` 全表都是 `u16` 小值，高字节**恒为 0**（`0x03E390+i*4+3` 恒 `0x00`），没有第二个子表；`0x0211CC` 按 `u16` 整字读取，未做 `and #0xFF` | **否**（取值域也不支持：`0x8E` 若拆成 `0x00/0x8E` 仍越界 143→有效，但 `0x05`→`0x00/0x05` 无意义） |
| **H5** 内部命令号，表更长 | 白名单确实从 `0x03ED60` 开始（11 组 × 8 字节 → `0x03EDB8` 正好是 E0 表，字节级闭合）；`0x03ED58`–`0x03ED5F` 是 8 字节填充（`…00 00 00 02`），其 `handler` 字段 = `0x00000002` < 代码区，不可能是合法 handler | **否** |

`H1` 与 `H2` 的证伪可以用一句话概括：**`0x03EBC0` 只被顺序遍历，从来没有"取第 n 条"的代码，所以任何"索引"假设都无消费者。**

## 4. `0x03EBC0` 的真实机制：顺序微操作链，不是命令表

`0x025A56` 是唯一读 `0x03EBC0` 的函数：

```asm
0x025A60  mov.l     er0, er6          ; er0 = 参数缓冲
0x025A62  mov.w     r1, r4            ; r4 = 总长度
0x025A64  mov.l     @(0x16,sp), er5   ; er5 = 已消耗计数指针
0x025A72  mov.l     #0x0003ebc0, er6  ; 链起点
0x025A78  mov.w     r4, e4
0x025A7A  dec.w     #1, e4            ; 预算-1
0x025A7C  bt        0x025ac6
0x025A7E  sub.w     r0, r0            ; 本条消耗数 = 0
0x025A80  mov.w     r0, @sp
0x025A88  mov.w     e4, r1            ; r1 = 预算
0x025A8A  mov.l     er6, er0          ; er0 = &record
0x025A8C  mov.l     @(0x4,er6), er2   ; er2 = record.handler
0x025A92  jsr       er2               ; handler(&record, budget, &consumed)
0x025A96  mov.b     r0l, r0l
0x025A98  bne       0x025aae          ; 返回 0 → 失败
0x025AA2  mov.w     #0x0053, r0
0x025AA6  mov.w     r0, @0x400436     ; 状态 0x53
0x025AB8  mov.w     @er5, r0
0x025ABC  cmp.w     r0, r4            ; 已消耗 >= 总长 → 结束
0x025ABE  bls       0x025ace
0x025AC0  add.l     #0x00000010, er6  ; ← 步长 16，顺序下一条
0x025AC6  mov.l     @(0x4,er6), er0
0x025ACC  bne       0x025a7e          ; handler != 0 继续
```

`0x025A56` 的唯一调用者是 `0x025270`（`bsr`），而 `0x025270` 属于 `0x02510C` = SCSI `0x24` SET WINDOW handler。

**结论**：这 26 条记录是「参数流解析微程序」——每条 `[op:参数 ID][len:该参数占字节数][handler:解析器][lo,hi:取值范围]`。26 条 `len` 之和 = **62 字节**，正好是一条 SET WINDOW 参数块的最大长度。`op` 值是**参数 ID（稀疏编号 0x00..0x39）**，不是命令号；因此"内部命令表"这个叫法本身要废止。

> 这也顺带解释了 `0x03E518` 的 10 条 `[id][flags][size][addr][mask]`：那是**另一张**按 ID 描述的参数表（供 `0x022F44` 用），与 `0x03EBC0` 的 `op` 编号共享同一套 ID 空间（`0x03`/`0x81`/`0x84`/`0x87`/`0x88`/`0x8A`/`0x8C`/`0x8D`/`0xE0`），进一步印证 `op == 参数 ID`。

## 7. `host_code` 高字节 = 命令类别？

`host_code` 高字节共 15 个取值，分布极不均匀：

| 高字节 | 条数 | 低字节 | 形态 |
|---|---|---|---|
| `0x08` | **44** | `00 10 30–34 40–44 50–54 60–64 70–74 80–84 91–94 A1–A4 B1–B4` | 唯一"矩阵式"族：`(30..B4)` × `(0..4)` |
| `0x06` | 10 | `00–04 10–14` | 两组 ×5 |
| `0x09` | 9 | `10–14 20 30 40 50` | 一组 ×5 + 四个单点 |
| `0x0F` | 6 | `10 20 30 40 50 60` | 六个单点 |
| `0x01` | 4 | `10 20 21 22` | 单点 |
| `0x05` | 3 | `00 01 02` | 单点 |
| `0x04 0x0E 0x10 0x11 0x20 0x30 0x40 0x50 0x90` | 各 1 | 全部 `0x00`（`0x0430` 例外） | 单点 |

`[实证]` 高字节确实是**族编号**：同族内 `field2` 连续（`0x0F10→0x20, 0x0F20→0x21`；`0x0830..0834→0x15..0x19`），且同族的 `kind` 与 `b3` 相同（`0x06xx` 全族 `kind=0x0311`，`b3=0x00`；`0x086x..0x08Bx` 全族 `kind=0x0460`，`b3=0x00`）。
`[推断]` 低字节在 `0x08` 族里编码"轴/通道(0–4) × 参数组"，因为 `b4` 的高半字节随低字节走 `{0,1,2,3,9}`、低半字节随组走。

**与主机侧 MAID 能力分组的对照：本轮无法完成** —— `03_analysis/md3/dispatch_caps.json` 在任务执行时**尚不存在**（该目录只有 `anchors.json`/`cfg_dispatch.*`/`cfg_funcs.txt` 等中间产物），按约束跳过，未作任何猜测性对齐。留给接手者：拿到 `dispatch_caps.json` 后，直接把 `host_code` 高字节与能力组的 selector 高位比对即可（本表已给出全部 15 个高字节取值）。

## 9. 未解疑问

1. **`[b1b2]` 的语义**：12 种 `kind`（`0x0161`…`0x0462`）在 `0x449AF1..F4` → `0xAA` 状态块的偏移 `0x12..0x15` 落地，但该状态块由谁发出（SCSI `0xE1` 读状态？诊断页？）未追。下一步：沿 `0x016F46` 的调用者向上找，看 `er5` 输出缓冲挂在哪个 CDB handler。
2. **`0x400436` 的双重身份**：它既被 `0x020EA0` 起的分派器写 `0x70/0x02/0x51/0x4F/0x03/0x66/0x65/0x56/0x7A/0x7B`（像 sense），又被 `0x022AFE`/`0x022C00` 当 `0x01914A` 的索引（≤0x8E）。两者能同时成立只能解释为"该单元存的是同一套 0x00–0x8E 编号的状态/命令码"，但 `0x70` 这类值落在表的 `0x06 0x0B 0x4E 0x00 0x00` 记录上是否真的有意为之，缺一个能双向印证的调用序列。**两个假设（状态码 / 命令码）都能自洽，缺 `0x400436` 写入者的时序证据。**
3. **`0x03E5D8` 块的结构**：0x24 步长的记录 + 变长首条（13 对），`0x024086` 用 `+0x03E62C −0x240` 的写法暗示"索引基值 0x10"。它显然是 E0/子功能的分派表候选（键形如 `0x4000/0xC800/0xD100`），但与本轮 `field2` 无关，未展开。
4. **`0x03ED58` 的 `00 00 00 02`**：作为第 27 条记录其 `handler = 0x00000002` 非法。若 SET WINDOW 的 62 字节全被消费则永不触达；但若某条 handler 少报消耗，就会 `jsr 0x00000002`。是"填充"还是"未被检出的越界隐患"，需动态验证。
5. **`0x01914A` 中 59 条未被 `host_code` 引用的记录**（主要在 `0x4D`–`0x7D` 区间，`kind` 为 `0x0500/0x051A/0x0520/0x0B43/0x0B47` 等）由谁索引——很可能是 `0x400436` 那条"状态码"通道，与疑问 2 是同一个问题。
